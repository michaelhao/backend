shop-management Specification

商店列表搜尋分頁、編輯更新、統一編號認證與儲存時伺服端重驗的完整行為規格
威脅模型：內部後台、非公網暴露（brute-force 不在 scope）；能登入後台者即為受信任的內部人員。正式環境無對外網際網路連線——政府商工登記 API 為全站唯一外部呼叫，於正式環境必定失敗（已知限制，R14）。

列表與搜尋

R1商店列表

系統 SHALL 在 GET /shops（需 Shop.index 權限）顯示商店分頁列表，依 id 升冪排列並 eager load admin 與 grade，每筆 SHALL 含商店名稱、版本名稱（無版本顯示「-」）、狀態 badge（中文 label 由 ShopStatus::label() 提供）與認證狀態。已認證（business_number 非 NULL）SHALL 顯示可點擊 badge，點擊開啟顯示統一編號與公司名稱的詳情 Modal；未認證 SHALL 顯示不可點擊的灰色 badge。
有權限者可見商店列表ShopRuTest::admin_can_access_shop_index
GIVEN持有 Shop.index 權限的 Admin 使用者
WHENGET /shops
THEN系統回應 200 並渲染商店列表
Viewer 具列表權限可見商店列表ShopRuTest::viewer_can_access_shop_index
GIVEN持有 Viewer 角色（含 Shop.index）的使用者
WHENGET /shops
THEN系統回應 200 並渲染商店列表

R3列表搜尋篩選

列表 SHALL 支援四個篩選條件且彼此交集：keyword 對商店名稱模糊比對（LIKE %v%）；grade_id 精準比對；business_number 對管理員統一編號精準比對；is_certified 為 '1' 時篩選統一編號非 NULL、'0' 時篩選統一編號為 NULL。篩選值 SHALL 於表單與分頁連結間保留。
關鍵字模糊比對商店名稱ShopRuTest::index_filters_by_keyword_with_partial_match
GIVEN名稱分別為「正品旗艦店」與「精選商行」的兩家商店
WHENGET /shops?keyword=旗艦
THEN列表僅含「正品旗艦店」
版本精準篩選ShopRuTest::index_filters_by_grade_id
GIVEN隸屬不同版本的兩家商店
WHENGET /shops?grade_id={id}
THEN列表僅含該版本的商店
統一編號精準篩選ShopRuTest::index_filters_by_exact_business_number
GIVEN管理員統編分別為 12345678 與 87654321 的兩家商店
WHENGET /shops?business_number=12345678
THEN列表僅含統編完全相符的商店
認證狀態篩選ShopRuTest::index_filters_by_certification_status
GIVEN一家已認證（統編非 NULL）與一家未認證的商店
WHENGET /shops?is_certified=1（或 =0）
THEN列表僅含對應認證狀態的商店
多條件交集ShopRuTest::index_combined_filters_intersect
GIVEN多家商店僅其一同時滿足 keyword 與 grade_id 條件
WHENGET /shops?keyword=...&grade_id=...
THEN列表僅含同時滿足所有條件的商店

R4分頁與每頁筆數

列表 SHALL 分頁，per_page 僅接受白名單 [50, 100, 150, 200]，未帶或非法值 SHALL 回退 50。切換每頁筆數的隱藏表單 SHALL 帶上所有現存篩選值——判斷依據為「非 null 且非空字串」，falsy 但有意義的 is_certified=0 MUST NOT 被遺漏。
合法 per_page 生效ShopRuTest::index_accepts_valid_per_page
WHENGET /shops?per_page=100
THEN每頁筆數為 100 且選單顯示 100 為選取狀態
非法 per_page 回退 50ShopRuTest::index_invalid_per_page_falls_back_to_50
WHENGET /shops?per_page=999
THEN每頁筆數為 50
切換每頁筆數保留未認證篩選ShopRuTest::per_page_form_preserves_uncertified_filter
WHENGET /shops?is_certified=0
THEN每頁筆數表單含 name="is_certified" value="0" 的隱藏欄位

存取控制

R2權限控管

四條商店管理路由 SHALL 受 auth middleware 與 RequiresPermission attribute 保護：index 需 Shop.index、edit/update/certify 需 Shop.update。未登入或無對應權限者 SHALL 被導離，且資料不得被變更。
未登入者被導向登入頁ShopRuTest::guest_is_redirected_to_login
WHEN訪客 GET /shops
THEN系統回應 302 導向 /login
無 update 權限者不可見編輯頁ShopRuTest::viewer_cannot_access_shop_edit
GIVEN僅持有 Viewer 角色權限的使用者
WHENGET /shops/{id}/edit
THEN系統回應 302 導離

編輯與更新

單一表單分商店／管理員兩區塊；敏感欄位遮蔽顯示，更新走欄位白名單與資料庫交易。

R5編輯表單與資料遮蔽

GET /shops/{id}/edit（需 Shop.update 權限）SHALL 渲染單一表單、分「商店基本資料」與「商店管理員基本資料」兩區塊。管理員 email SHALL 解密後以 Mask::email() 遮蔽顯示（點「修改」才切換為可輸入）；統一編號 SHALL 以 Mask::string() 遮蔽顯示於 readonly 欄位；公司名稱為 readonly。狀態下拉 SHALL 由 ShopStatus::cases() 渲染並以 label() 顯示中文。
編輯表單預填並遮蔽敏感欄位ShopRuTest::admin_can_access_shop_edit
GIVEN既有商店與其管理員
WHENGET /shops/{id}/edit
THEN系統回應 200，表單含商店 name、email、grade、status 與管理員 name
AND管理員 email 以遮蔽形式顯示

R6更新商店

PUT /shops/{id}（需 Shop.update 權限）SHALL 以 ShopUpdateRequest 驗證：name 必填、最長 50 字元；email 必填、email 格式且不得與其他商店重複（unique 排除自身 ignore($this->route('id'))）；grade_id 必填且須存在（變更時限 Active，見 R9）；status 必填且須為合法 ShopStatus 值；admin.name 必填、最長 20 字元；admin.email 必填、email 格式；admin.business_number 選填、8 位數字；admin.company_name 選填。商店與管理員的更新 SHALL 在同一資料庫交易內完成；商店無管理員記錄時 SHALL 僅更新商店本身、不得出錯。成功 SHALL 302 導向 /shops 並帶 success flash「商店已更新」。
成功更新商店與管理員ShopRuTest::admin_can_update_shop
GIVEN持有 Shop.update 權限的使用者
WHENPUT /shops/{id} 帶合法的商店與管理員欄位
THEN系統回應 302 導向 /shops 並帶 success flash
ANDshops 與 shops_admin 資料已更新
商店 email 與他店重複被拒ShopRuTest::update_fails_with_duplicate_shop_email
GIVEN兩家既有商店
WHENPUT 更新其中一家的 email 為另一家的 email
THENsession errors 包含 email
商店 email 維持自身值允許ShopRuTest::update_allows_same_shop_email_for_self
GIVEN既有商店
WHENPUT /shops/{id} 帶與自身相同的 email
THEN更新成功、無驗證錯誤
status 非法值被拒ShopRuTest::update_fails_with_invalid_status
WHENPUT /shops/{id} 帶不在 ShopStatus 內的 status
THENsession errors 包含 status
grade_id 不存在被拒ShopRuTest::update_fails_with_nonexistent_grade_id
WHENPUT /shops/{id} 帶不存在的 grade_id
THENsession errors 包含 grade_id
無管理員的商店仍可更新ShopRuTest::update_shop_without_admin_does_not_fail
GIVEN一家沒有 shops_admin 記錄的商店
WHENPUT /shops/{id} 更新商店基本資料
THEN系統回應 302 並帶 success flash
AND商店資料已更新

R7表單欄位白名單

更新 SHALL 僅寫入通過驗證的欄位：商店欄位取 $request->safe()->only(['name','email','grade_id','status'])、管理員欄位取 validated()['admin']。未在驗證規則內的欄位（如 admin[password]、admin[shop_id]）MUST NOT 經此表單寫入資料庫。
未驗證欄位被忽略ShopRuTest::update_ignores_unvalidated_admin_fields
GIVEN既有商店管理員
WHENPUT /shops/{id} 額外夾帶 admin[password] 與 admin[shop_id]
THEN更新成功
AND管理員的 password 雜湊值與 shop_id 維持原值

R9版本變更規則

變更 grade_id 時 SHALL 僅允許指向 Active 狀態的版本；維持原 grade（即使該版本已停用）SHALL 允許送出，否則表單將永遠無法儲存。grade 實際變更時系統 SHALL 觸發商店 addon 同步（ShopAddonSyncService，同步規則屬 addons 範疇，本 spec 僅規範此交界）。
指派停用版本被拒ShopRuTest::update_fails_when_assigning_inactive_grade
GIVEN一個 Inactive 狀態的版本
WHENPUT /shops/{id} 將 grade_id 變更為該版本
THENsession errors 包含 grade_id
維持原有的停用版本允許ShopRuTest::update_allows_keeping_existing_inactive_grade
GIVEN商店現有版本已被停用
WHENPUT /shops/{id} 帶原本的 grade_id
THEN更新成功、無驗證錯誤

統編認證

certify 端點僅供前端預覽公司名稱；實際寫入以儲存時的伺服端重驗為準，表單送來的公司名稱不被信任。

R10儲存時伺服端重驗認證

認證資料 SHALL 以伺服端為準，表單送來的 admin[company_name] MUST NOT 被直接信任寫入。儲存時依 admin[business_number] 分流：未帶該欄位 → 兩欄皆不異動；為空值 → business_number 與 company_name 一併存 NULL；與 DB 現值相同 → company_name 取 DB 現值、不發認證 API；有變更 → 伺服端重新呼叫認證 API，失敗 SHALL 拋 ValidationException（errors 含 admin.business_number，訊息「統一編號認證失敗，請重新進行認證」），成功 SHALL 以 API 回傳的公司名稱寫入。
認證後儲存寫入 DBShopRuTest::certification_data_saved_to_db
GIVEN認證 API 回傳成功（Http fake）
WHENPUT /shops/{id} 帶新的 admin[business_number] 與 admin[company_name]
THENshops_admin 的 business_number 與 company_name 已寫入
統編變更時重驗並採用 API 公司名稱ShopRuTest::update_reverifies_changed_business_number_and_uses_api_company_name
GIVEN認證 API 回傳公司名稱「API 正確公司」（Http fake）
WHENPUT /shops/{id} 變更統編且表單夾帶偽造的 admin[company_name]
THENshops_admin 的 company_name 為「API 正確公司」而非表單值
統編重驗失敗被拒ShopRuTest::update_rejects_business_number_that_fails_verification
GIVEN認證 API 回傳空結果（Http fake）
WHENPUT /shops/{id} 變更統編
THENsession errors 包含 admin.business_number
ANDshops_admin 的統編維持原值
統編未變更不發認證 APIShopRuTest::update_unchanged_business_number_keeps_company_name_without_api_call
GIVEN既有已認證的商店管理員
WHENPUT /shops/{id} 帶與 DB 相同的統編
THEN未發出任何 HTTP 請求
ANDcompany_name 維持 DB 現值

R11統一編號認證端點

POST /shops/{id}/certify（需 Shop.update 權限，fetch JSON 請求）SHALL 以 ShopCertifyRequest 驗證 business_number 必填且為 8 位數字，不合法回 422。通過後 SHALL 呼叫政府商工登記 API 查詢：查得 SHALL 回 JSON {"success": true, "company_name": "..."}；查無資料 SHALL 回 {"success": false}。找不到商店 SHALL 回 404 與 JSON {"success": false, "message": "找不到該商店"}。
此端點僅供前端預覽公司名稱；實際寫入以儲存時的伺服端重驗（R10）為準。
缺少統一編號回 422ShopRuTest::certify_missing_business_number_returns_422
WHENPOST /shops/{id}/certify 不帶 business_number
THEN系統回應 422 驗證錯誤
統一編號格式錯誤回 422ShopRuTest::certify_invalid_business_number_returns_422
WHENPOST /shops/{id}/certify 帶非 8 位數字（含字母或位數不符）
THEN系統回應 422 驗證錯誤
認證成功回傳公司名稱ShopRuTest::certify_success_returns_company_name
GIVEN政府 API 回傳該統編的公司資料（Http fake）
WHENPOST /shops/{id}/certify 帶合法統編
THEN系統回應 JSON {"success": true, "company_name": "..."}
查無資料回傳失敗ShopRuTest::certify_empty_response_returns_failure
GIVEN政府 API 回傳空陣列（Http fake）
WHENPOST /shops/{id}/certify 帶合法統編
THEN系統回應 JSON {"success": false}
認證不存在的商店ShopRuTest::certify_nonexistent_shop_returns_404_json
WHENPOST /shops/99999/certify 帶合法統編
THEN系統回應 404 與 JSON {"success": false, "message": "找不到該商店"}

刻意設計與已知限制（不是缺漏）

以下為刻意的設計決策與已知限制，避免後人誤判為待補項目或 bug。

R8管理員 email 加密與應用層唯一性（刻意設計）

管理員 email SHALL 以 encrypted cast 加密儲存（密碼為 hashed cast）；DB 層 MUST NOT 對該欄位加 unique index——加密值不可比對。唯一性 SHALL 由 ShopService 於寫入前解密逐筆比對（排除自身），衝突時拋 ValidationException，errors 包含 admin.email（訊息「此 email 已被使用」）。
O(n) 解密比對為 encrypted cast 的必然取捨，內部後台 shops_admin 筆數有限，可接受。
管理員 email 與他店管理員重複被拒ShopRuTest::update_fails_with_duplicate_admin_email
GIVEN兩家商店各有管理員
WHENPUT 更新其中一位管理員的 email 為另一位的 email
THENsession errors 包含 admin.email
管理員 email 維持自身值允許ShopRuTest::update_allows_same_admin_email_for_self
GIVEN既有商店管理員
WHENPUT /shops/{id} 帶與自身相同的 admin[email]
THEN更新成功、無驗證錯誤

R12找不到 id 的處理（刻意設計）

路由 SHALL 採手動 {id} 查詢（ShopService::findShopById() 經 ShopRepository::getById()），MUST NOT 使用 route model binding——找不到時以應用語意回應而非空白 404 頁（源自 spec/7 的設計決策）：edit 與 update SHALL 302 導回 /shops 並帶 error flash「找不到該商店」；certify（fetch JSON 請求）SHALL 回 404 JSON（見 R11）。
certify 原為 302 redirect，會被 fetch 靜默跟隨、json() 解析失敗而誤顯示「認證失敗」；2026-06-12 設計 review 修正為 404 JSON，commit 40a5388。
編輯不存在的商店ShopRuTest::edit_nonexistent_shop_redirects_with_error
WHENGET /shops/99999/edit
THEN系統回應 302 導向 /shops 並帶 error flash「找不到該商店」
更新不存在的商店ShopRuTest::update_nonexistent_shop_redirects_with_error
WHENPUT /shops/99999
THEN系統回應 302 導向 /shops 並帶 error flash「找不到該商店」

R13無新增與刪除（刻意設計）

本功能僅支援列表（R）與編輯（U）。系統 MUST NOT 提供商店的新增（create/store）與刪除（destroy）路由——商店帳號由商店端系統開立，後台僅管理既有商店。sales_id 與 expired_at MUST NOT 在本 UI 編輯（屬 bills 範疇）。
無新增路由ShopRuTest::store_route_does_not_exist
WHENPOST /shops
THEN系統回應 405（Method Not Allowed）
無刪除路由ShopRuTest::delete_route_does_not_exist
WHENDELETE /shops/{id}
THEN系統回應 405（Method Not Allowed）

R14已知限制——政府 API 與無對外連線環境

統編認證 SHALL 呼叫政府商工登記 API（http://data.gcis.nat.gov.tw/od/data/api/5F64D864-61CB-4D0D-8AD9-492047CC1EA6，timeout 10 秒），此為全站唯一的外部 HTTP 呼叫。呼叫 SHALL 以 try/catch 包裹，任何連線失敗 SHALL 回 {"success": false}、MUST NOT 拋出 500。
已知限制：正式環境無對外網際網路連線，certify 與儲存時重驗在正式環境必回失敗、認證資料無法於正式環境經此流程寫入（2026-06-12 裁示：不改程式碼、僅記載；功能於可連外的開發/測試環境正常運作）。
連線失敗回傳失敗而非 500ShopRuTest::certify_connection_exception_returns_failure
GIVEN對政府 API 的連線拋出 ConnectionException（Http fake）
WHENPOST /shops/{id}/certify 帶合法統編
THEN系統回應 JSON {"success": false}

—刻意不做的事（彙整）

商店新增／刪除商店帳號由商店端系統開立，後台僅管理既有商店；POST/DELETE 回 405（R13）
Route model binding保留 {id} + redirect-with-flash UX，certify 走 404 JSON（R12）
admin email 的 DB unique indexencrypted cast 加密值不可比對，唯一性由應用層解密比對（R8）
信任表單的 company_name認證資料以伺服端為準，公司名稱一律採 API 回傳值或 DB 現值（R10）
