開發功能逐步手冊(整合版)

本專案在裝了 superpowers 之後的開發功能 SOP:把既有的 OpenSpec / spec-* 流程當骨架,疊上 superpowers 的紀律層。每一步都寫明:呼叫什麼指令/skill、要提供什麼內容、產出什麼。
怎麼用這頁:照「開發功能手冊」的步驟順序做事;每一步的卡片給你「呼叫 / 提供 / superpowers 疊加 / 產出」。需要某個 skill 的細節時,點進下方「Skill 字典」看完整規則。
既有流程:.claude/commands/opsx/*、.claude/commands/spec-*.md superpowers:github.com/obra/superpowers 各 SKILL.md(已裝)
人工整理的閱讀版;指令行為以 .claude/commands/* 為準,superpowers 規則以官方 SKILL.md 為準。

這份文件與核心理念

先理解 superpowers 怎麼運作,再讀下方逐步流程。

運作前提:Skill 優先 (using-superpowers)

superpowers 的骨幹是一組可組合的 skill。它的第一條規則是:只要有 1% 機率某個 skill 可能適用,就必須先 invoke 該 skill 再回應 —— 連澄清問題、探索 codebase 之前都要先查 skill,因為「skill 會告訴你該怎麼探索、怎麼問」。invoke 後若發現不適用,再放下即可。
指令優先序(高 → 低):① 使用者明確指令(CLAUDE.md / 直接要求) ② superpowers skills ③ 預設系統提示。若 CLAUDE.md 說「別用 TDD」而 skill 說「一律 TDD」,聽使用者的 —— 使用者永遠在控制權上。
兩種 skill 型別 / 觸發順序
  • RIGID 嚴格型(如 TDD、debugging):一字不差照做,不可把紀律「調整掉」。
  • FLEX 彈性型(模式類):依情境調整原則。skill 本身會告訴你它屬哪一型。
  • 多個 skill 都適用時:先 process skill(brainstorming / debugging — 決定「怎麼 approach」),再 implementation skill(決定「怎麼執行」)。
    「來做 X」→ 先 brainstorming;「修這個 bug」→ 先 debugging。

Track A:開發新功能(逐步)

每張卡固定四欄:呼叫(下什麼指令 / 哪個 skill)、提供(要餵什麼)、疊加(套哪個 superpowers 紀律)、產出。標題的 ★ 表示這步是 superpowers 新增的環節。

Track A · 新功能:從想法到歸檔

1探索與設計

呼叫/opsx:explore <題目> 進思考模式(可順手產 OpenSpec artifacts);搭配 superpowers Skill brainstorming
提供想做什麼 / 要解決的問題(一句也行)。例:/opsx:explore 後台批次匯出帳單
疊加brainstorming 的 HARD-GATE:在你核可設計前不寫任何 code;一次問一題、提 2–3 方案含推薦。
產出釐清過的需求與設計方向(尚未實作)。

2產出 change artifacts

呼叫/opsx:propose <kebab-name | 描述>
提供change 名稱(kebab-case,如 add-bill-export)或一段描述讓它自己命名。
疊加writing-plans 的標準:把 tasks.md 切成 2–5 分鐘一步、無 placeholder(不准 TBD / 「加上適當錯誤處理」)、每步含 TDD(先寫測試)。
產出openspec/changes/<name>/ 下的 proposal.md、design.md、tasks.md。

3拷問設計 選用

呼叫/grill-me [change-name]
提供要被壓力測試的 change 名稱(它會讀該 change 的 artifacts 當拷問素材)。
疊加等同 superpowers brainstorming 的增量驗證精神 —— 逐題解決決策樹,挑出矛盾與缺口。
產出修訂後的 artifacts(proposal / design / tasks 視情況更新)。

4建立隔離工作區 ★ superpowers 新增

呼叫harness 原生 EnterWorktree(優先);或 superpowers Skill using-git-worktrees
提供分支 / 工作區名稱(通常用 change name)。
疊加using-git-worktrees:先偵測是否已隔離 → 用原生工具(別用 git worktree add)→ 跑 baseline 測試確認起點全綠(失敗先回報)。
產出乾淨、隔離、測試通過的工作區,保護 master。

5spec 收尾

呼叫/spec-finalize <name>
提供change 名稱(省略則從 active change 推斷)。前提:artifacts 已存在。
疊加內含 openspec validate --strict + review skill 審 spec;對應 superpowers「先把規格定清楚再動工」。
產出驗證通過的 spec,並 commit docs(spec): propose <name>。

6實作(逐 task)

呼叫/spec-build <name>(內部跑 opsx:apply 逐 task 迴圈)
提供change 名稱。它會逐 task 實作,每 task 後跑 pint + 相關測試(Docker 內)。
疊加test-driven-development ★:每 task 先寫失敗測試 → 看它失敗 → 最小實作 → 看它通過。(可選)subagent-driven-development:每 task 派新 subagent + spec/品質兩階段審。卡關時走步驟 6-bug。
產出逐 task 勾選的實作,測試全綠、pint 過;不自動 commit。

6·bug遇 bug / 測試失敗時 ★ superpowers 新增

呼叫superpowers Skill systematic-debugging
提供錯誤訊息 / 失敗測試 / 重現步驟。
疊加鐵律:先根因再修。四階段:根因調查 → 模式分析 → 單一假設最小測試 → 寫失敗測試後只改一處。修 3 次仍不好 → 停下質疑架構。
產出治根因的修正 + 防回歸測試,然後回步驟 6 繼續。

7審查與回應 finding

呼叫由 /spec-build 全 task 完成後自動跑 review(實作 vs spec)+ simplify
提供無需額外輸入;review 對整個 branch diff 比對 openspec/changes/<name>/ 的 spec。
疊加收 finding 時套 receiving-code-review:先查證再改、不說「你說得對」、不感謝;不清楚先全部澄清;違反 YAGNI 的建議先 grep 有沒有人用。
產出實作與 spec 一致;reuse / 冗餘已處理。偏離 spec 時停下討論「修實作還是改 spec」。

8完成前驗證 ★ superpowers 新增

呼叫superpowers Skill verification-before-completion
提供無;這是宣稱「完成」前的自我 gate。
疊加鐵律:沒在這一刻跑過驗證指令,就不能說它過。跑全測試 docker compose exec backend-api php artisan test --compact、pint,讀完整輸出 / 退出碼,才宣稱完成。
產出附證據的「完成」狀態(N/N 測試通過、pint 乾淨)。

9Commit(人工)

呼叫手動 git commit(/spec-build 刻意不自動 commit)
提供自訂顆粒度與訊息;重構與行為修正分開 commit。
疊加CLAUDE.md commit 紀律:commit 訊息逐項對得上 staged diff(不要有幽靈項目);用 HEREDOC。
產出乾淨、可追溯的 commit。

10歸檔與收尾

呼叫/spec-ship <name>(內部跑 opsx:archive)
提供change 名稱。它會 sync delta spec → openspec/specs/、移到 archive/、從 proposal.md 的 ## Why 產 commit。
疊加整體收尾決策參考 finishing-a-development-branch:先確認測試全綠,再決定 merge / 開 PR / 保留 / 丟棄。不自動 push。
產出已歸檔的 change、合併進主 specs、收尾 commit;branch 可推送 / 開 PR。

Track B:既有功能回填

用在「已經有實作、但 spec 還沒進 OpenSpec」的舊功能;新功能請走 Track A。

Track B · 既有功能:補 spec + 文件

R回填一個既有功能

呼叫/spec-retrofit <feature>
提供既有功能名(如 roles、grades、users、shops、bills)。前置:routes 與 Controller 已存在(否則改走 Track A)。
疊加Phase 1 全面設計 Review(分層架構 / 安全 / 測試覆蓋 / 與舊 spec 落差)結束必停等你裁示;只修核可項目;刻意設計要寫成 MUST NOT Requirement。
產出openspec/specs/<capability>/spec.md + 互動式 docs/<feature>-spec.html(零外部資源,/docs 可瀏覽)。

Skill 字典:主線

以下是 superpowers 各 skill 的完整規則,供手冊各步驟查閱細節。

1腦力激盪 brainstorming SKILL

把點子透過自然的協作對話變成成形的設計與規格。這是所有實作的第一道關卡。
HARD-GATE:在提出設計並取得使用者核可前,不得 invoke 任何實作 skill、不得寫 code、不得 scaffold。再簡單的專案也適用(設計可以只有幾句話,但一定要呈現並取得同意)。
流程步驟brainstorming
  • 探索專案脈絡(檔案、文件、近期 commit)。
  • (若接下來是視覺題)單獨一則訊息提供「視覺輔助」選項。
  • 一次只問一個澄清問題,聚焦目的 / 限制 / 成功標準;盡量用多選題。
  • 提出 2–3 個方案含取捨,先講你推薦哪個與原因。
  • 分段呈現設計,每段都先取得認可才往下;涵蓋架構、元件、資料流、錯誤處理、測試。
  • 寫 design doc 到 docs/superpowers/specs/YYYY-MM-DD-<topic>-design.md 並 commit。
  • spec 自我審查:掃 placeholder / 前後矛盾 / 範圍是否該拆 / 歧義,當場修。
  • 請使用者審 spec,核可後才進下一步。
終點唯一:brainstorming 之後只能接 writing-plans,不可直接跳任何實作 skill。原則:一次一問、YAGNI、先探索替代方案、增量驗證。

2隔離工作區 using-git-worktrees SKILL

確保工作在隔離工作區進行,保護你當前的分支不受影響。核心順序:先偵測是否已隔離 → 用平台原生工具 → 最後才退回 git worktree。別跟 harness 對著幹。
流程步驟using-git-worktrees
  • Step 0 偵測既有隔離:比對 git-dir 與 git-common-dir(並排除 submodule);若已在 worktree 就跳過建立。在一般 repo 則先徵得同意。
  • Step 1 建立:1a 優先用原生工具(如 EnterWorktree)—— 有原生工具卻用 git worktree add 是第一大錯;1b 無原生工具才退回 git,目錄優先序 .worktrees/,並用 git check-ignore 確認已被忽略。
  • Step 3 專案設定:自動偵測並安裝相依(npm install / cargo build / pip install / go mod download)。
  • Step 4 驗證乾淨 baseline:跑測試確認起點全綠;失敗就回報並詢問是否繼續(以便日後分辨新 bug 與既有問題)。

3寫實作計畫 writing-plans SKILL

寫一份假設工程師對本 codebase 零背景的詳盡計畫:每個任務要動哪些檔、附上實際 code、怎麼測。把整份工作切成一口一口的小任務。原則:DRY、YAGNI、TDD、頻繁 commit。存到 docs/superpowers/plans/YYYY-MM-DD-<feature>.md。
bite-sized 任務(每步 2–5 分鐘):寫失敗測試 → 跑它確認失敗 → 寫剛好能過的最小實作 → 跑它確認通過 → commit。
關鍵規則writing-plans
  • 先盤點檔案結構:動工前列出要建/改哪些檔、各自單一職責;偏好小而專注的檔案。
  • No Placeholders(計畫失敗):不准 TBD/TODO、不准「加上適當錯誤處理 / 驗證」、不准「為上面寫測試」卻沒附測試碼、不准引用未定義的型別或函式。改 code 的步驟一定要附上 code。
  • 自我審查:spec 覆蓋率(每個需求都有對應任務嗎)、placeholder 掃描、型別/命名前後一致。
  • 交接:提供兩種執行選項 —— subagent-driven(推薦)或 inline(executing-plans)。

4執行計畫 subagent-driven-development / executing-plans SKILL

把計畫逐任務執行。有兩種模式,視平台是否支援 subagent 而定。
模式 A:Subagent 驅動(推薦)subagent-driven-development
  • 每個任務派一個全新 subagent:不繼承你的對話史,你精準裁切它需要的 context —— 保持它聚焦,也保留你自己的 context 做協調。
  • 兩階段審查:實作完先做 spec 合規審(有沒有少做 / 多做),通過後再做 code quality 審。審出問題由同一 implementer 修、再審,直到過才換下一任務。
  • 連續執行:任務間不要停下來問「要繼續嗎」;只有 BLOCKED 無法解、真正卡住、或全部完成才停。最後對整體再派一次 final review,然後進收尾。
  • implementer 四種狀態:DONE / DONE_WITH_CONCERNS / NEEDS_CONTEXT / BLOCKED,各有對應處置;絕不讓同一 model 無變更地重試。
  • 選 model:機械性任務(1–2 檔、規格完整)用便宜快的;整合/判斷用標準;架構/設計/審查用最強。
模式 B:Inline 執行(無 subagent 時)executing-plans
  • 載入計畫 → 批判式檢視(有疑慮先提出)→ 建 TodoWrite → 逐任務照步驟執行、不跳驗證。
  • 卡住(缺相依、測試失敗、指令不清)就停下來問,不要用猜的硬幹。
  • 完成後進 finishing-a-development-branch。
共同紅線:未經明確同意,絕不在 main/master 上開工。

品質防線(貫穿全程)

5測試驅動開發 test-driven-development RIGID

先寫測試、看它失敗、再寫剛好能過的最小 code。核心原則:沒看著測試失敗過,就不知道它測對了東西。
鐵律:NO PRODUCTION CODE WITHOUT A FAILING TEST FIRST。先寫了 code?刪掉重來 —— 不留作參考、不一邊改一邊「適應」它。刪就是刪。

RED → GREEN → REFACTOR

RED寫一個最小失敗測試
看它失敗是因功能缺失
而非 typo
GREEN寫剛好能過的最小 code
看它通過其他測試仍綠
輸出乾淨
REFACTOR清理、保持綠
不加新行為
好測試:一次一個行為、命名清楚、展示意圖、用真 code(萬不得已才 mock)。例外(須先問人):拋棄式原型、產生的 code、設定檔。

6系統化除錯 systematic-debugging RIGID

隨機試錯既浪費時間又生新 bug。一律先找到根因,再動手修;治標就是失敗。
鐵律:NO FIXES WITHOUT ROOT CAUSE INVESTIGATION FIRST。沒完成第一階段,就不准提任何修法。
四個階段(逐一完成才往下)systematic-debugging
  • ① 根因調查:仔細讀錯誤訊息 / stack trace;穩定重現;查近期變更;多元件系統在每個邊界加診斷 log 找出「哪一層壞」;回溯資料流到源頭,修在源頭而非症狀。
  • ② 模式分析:找同 codebase 的可用範例、完整讀參考實作(別只掃)、列出「可用 vs 壞掉」的每個差異、釐清相依。
  • ③ 假設與測試:提出單一假設(「我認為 X 是根因,因為 Y」)、做最小改動只測一個變數、驗證後才前進,不在上面疊修法。
  • ④ 實作:先寫失敗測試(用 TDD)→ 只改一處治根因(不順手重構)→ 驗證。同一 bug 修 3 次還不好 → 停,質疑架構,不要硬上第 4 次。

7請求 Code Review requesting-code-review SKILL

派一個 code reviewer subagent,給它精準裁切的 context(不是你的對話史),在問題擴散前就抓住它。原則:review early, review often。
何時與怎麼做requesting-code-review
  • 強制:subagent 驅動的每個任務後、完成大功能後、merge 進 main 前。選用但有價值:卡住時、重構前、修完複雜 bug 後。
  • 取 BASE_SHA / HEAD_SHA → 用 reviewer 模板派 subagent(描述、需求、起訖 SHA)。
  • 依嚴重度處理:Critical 立刻修、Important 前進前先修、Minor 記下日後處理;reviewer 錯了用技術理由 push back。

8接收 Code Review receiving-code-review SKILL

收到 review 回饋時要做技術評估,不是情緒表演,也不是盲目照做。核心:先查證再實作、先發問再假設,技術正確優先於社交舒適。
回應流程:READ(讀完不急著反應)→ UNDERSTAND(用自己的話複述需求或發問)→ VERIFY(對照 codebase 現實)→ EVALUATE(對「這個」codebase 技術上成立嗎)→ RESPOND(技術性認可或有理由的反駁)→ IMPLEMENT(一次一項,各自測)。
禁語與要點receiving-code-review
  • 禁語:「你說得完全對!」「好點子!」「我馬上做」(未驗證前)、任何「謝謝」。改成:複述需求 / 發問 / 用技術理由反駁 / 直接動手並說「Fixed: …」。
  • 不清楚就先全部澄清再動工 —— 項目可能彼此相關,半懂等於做錯。
  • 外部回饋要存疑、查證:會不會弄壞既有功能?有沒有現行實作的理由?跨平台都成立嗎?reviewer 懂完整脈絡嗎?
  • YAGNI 檢查:reviewer 要你「做完整」時先 grep 有沒有人用;沒人用就提議移除。

9完成前驗證 verification-before-completion RIGID

沒驗證就宣稱完成,是不誠實,不是有效率。核心:先有證據,再下結論。
鐵律:NO COMPLETION CLAIMS WITHOUT FRESH VERIFICATION EVIDENCE。沒在「這一則訊息裡」跑過驗證指令,就不能宣稱它通過。
Gate 函式與紅旗verification-before-completion
  • 宣稱任何狀態前:① 找出能證明的指令 ② 完整跑一次(全新、不偷)③ 讀完整輸出 / 退出碼 / 失敗數 ④ 確認輸出真的支持宣稱 ⑤ 才宣稱(並附上證據)。跳任一步 = 說謊。
  • 紅旗:用「應該 / 大概 / 看起來」;驗證前就「太好了 / 完美 / 搞定」;未驗證就 commit / push / PR;直接相信 agent 回報「成功」(要自己看 VCS diff 查證)。

收尾與進階

10收尾分支 finishing-a-development-branch SKILL

開發完成、測試全綠後,以結構化選項收尾。核心:驗測試 → 偵測環境 → 提選項 → 執行選擇 → 清理。
步驟與四個選項finishing-a-development-branch
  • Step 1 驗測試:先跑測試,失敗就停(不得 merge / PR)。
  • Step 2–3:偵測 worktree 狀態決定選單、判定 base branch。
  • Step 4 提「剛好這幾個」選項:① 本地 merge 回 base ② push 並開 PR ③ 維持原樣(之後自己處理) ④ 丟棄(需打字輸入 discard 確認)。
  • Step 5 執行:merge 要先驗證成功才清 worktree、再刪 branch;開 PR 則保留 worktree 供迭代。
  • Step 6 清理:只在選項 ①、④ 清理,且只清自己建立的 worktree(harness 建的不要動)。

平行派工 Agent dispatching-parallel-agents FLEX

面對 2 個以上彼此獨立、無共享狀態的問題(例如不同檔的測試失敗各有根因),一個問題派一個 agent 並行處理,而非循序逐一查。
適用 / 不適用 / 做法dispatching-parallel-agents
  • 適用:3+ 測試檔各有不同根因、多個獨立壞掉的子系統、每個問題不需其他脈絡即可理解。
  • 不適用:失敗彼此相關(修一個可能修好其他)、需要看全系統狀態、會互相干擾(改同一檔)。
  • 做法:切出獨立領域 → 每個 agent 給聚焦範圍 + 明確目標 + 約束(別動其他 code)+ 要求回傳摘要 → 並行派出 → 回來後檢查是否衝突、跑全測試整合。
