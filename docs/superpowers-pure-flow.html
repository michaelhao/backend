純 Superpowers 開發流程

官方 superpowers 5.1.0 的端到端開發生命週期——不含 OpenSpec / 專案 spec-* 包裝層
用途：供日後評估「走 Superpowers 流程 vs 專案現有流程（opsx → spec-finalize → build → ship）」。本頁只呈現 Superpowers 本身的流程,不做比較;比較留待評估時進行。
來源：~/.claude/plugins/.../superpowers/5.1.0/skills/*/SKILL.md 對照整合版：docs/superpowers-workflow.html
流程以官方 skill 內容為準。主線六階段循序進行,各階段以「鐵律 / Gate」把關;TDD、驗證、除錯、skill 探索為貫穿全程的隨身規則。

主線是一條由「設計核准」與「測試全綠」兩道 Gate 把關的管線;每個 task 內部都跑 TDD 與 review。

主線階段

P1brainstorming HARD GATE

何時：任何創造性工作前(新功能、元件、行為變更)。再簡單的東西也要走。

把想法經由協作對話收斂成設計與 spec。探索專案脈絡 → 一次問一個澄清問題(目的 / 限制 / 成功標準)→ 提出 2-3 個方案與你的建議 → 分段呈現設計、逐段取得同意。
GATE 在「呈現設計 + 使用者核准」之前,不得寫任何 code、scaffold、或呼叫任何實作 skill。「太簡單不用設計」是反模式。
產出 設計 spec 寫到 docs/superpowers/specs/YYYY-MM-DD-<topic>-design.md 並 commit;自我審查(placeholder / 矛盾 / 範圍 / 歧義)後,請使用者審 spec。
步驟
  1. 探索專案脈絡(檔案、docs、近期 commit)
  2. (若涉視覺)單獨一則訊息詢問是否開視覺輔助
  3. 一次一個澄清問題,聚焦目的 / 限制 / 成功標準
  4. 提 2-3 方案 + 建議(先講推薦的並說明理由)
  5. 分段呈現設計,每段取得同意;涵蓋架構 / 元件 / 資料流 / 錯誤處理 / 測試
  6. 寫設計 spec 並 commit
  7. spec 自我審查並修正
  8. 使用者審 spec(有改回頭修)
  9. 核准 → 轉進 writing-plans
→ 唯一下一步:writing-plans(不得跳到其他實作 skill)

P2writing-plans

何時:已有 spec / 需求、動 code 前。

寫一份「假設工程師完全不懂本專案」也能照做的實作計畫。先 map 檔案結構(每檔單一職責、檔案小而專注)→ 拆成 bite-sized 步驟(每步 2-5 分鐘),且每個 task 以 TDD 編排:寫失敗測試 → 跑它確認失敗 → 最小實作 → 跑測試確認通過 → commit。
無 placeholder 「TBD / 之後補 / 加適當錯誤處理 / 類似 Task N」皆為計畫失敗;每個 code 步驟都要有實際 code、確切指令與預期輸出。
產出 plan 寫到 docs/superpowers/plans/YYYY-MM-DD-<feature>.md;自我審查(spec 覆蓋率 / placeholder / 型別與命名一致性)。
→ 執行交接:選 subagent-driven-development(推薦)或 executing-plans

P3using-git-worktrees

何時:執行 plan 前,需要與目前工作區隔離。

確保工作在隔離環境進行。先偵測是否已在隔離區(比較 git rev-parse --git-dir 與 --git-common-dir,並排除 submodule)→ 已隔離就直接用;否則優先用平台原生 worktree 工具,沒有才退回手動 git worktree。核心原則:不與 harness 對抗。
在 main/master 上,未取得使用者同意不得開始實作。

P4執行 plan TDD REVIEW

何時:plan 寫好、工作區已隔離。兩種執行法二選一。

A. subagent-driven-development(推薦,同 session)：每個 task 派一個全新 subagent(乾淨 context,由你精準餵入所需資訊)→ implementer 走 TDD 實作、測試、commit、自審 → 兩階段審查:先「spec 合規」,通過後再「code quality」,審出問題就修到過再往下 → 標記完成。全部 task 完成後派 final reviewer 總審。連續執行,不在 task 之間中途請示。
B. executing-plans(另開 session,批次 + 檢查點)：載入 plan → 批判性檢視(有疑慮先提)→ 逐 task 照步驟執行並跑驗證 → 遇 blocker / 指令不清就停下發問,不硬闖。
貫穿:每個 task 都受 TDD 鐵律約束;遇 bug 走 systematic-debugging(先寫重現測試再修)。
subagent-driven 每 task 迴圈
  1. 派 implementer subagent(給完整 task 文字 + 場景脈絡,不給你的對話史)
  2. 它有問題先答清楚,再讓它動工
  3. implementer 走 TDD 實作 → 測試 → commit → 自審
  4. 派 spec 合規 reviewer:確認不多做也不少做;有缺口 → implementer 修 → 再審
  5. spec 過了才派 code quality reviewer;有問題 → implementer 修 → 再審
  6. 兩審皆過 → 標記 task 完成 → 下一個 task
  7. 全部完成 → 派 final code reviewer → 進 finishing-a-development-branch
→ 完成後:requesting-code-review(最終)→ finishing-a-development-branch

P5requesting / receiving code review REVIEW

何時(mandatory):每個 task 後、完成大功能後、merge 前。

派 code reviewer subagent,給它精準裁切的 context(不給對話史),讓它聚焦在產出本身。依嚴重度處理回饋:Critical 立即修、Important 往下走前修、Minor 記錄;reviewer 判斷錯誤時可有理據反駁。原則:review early, review often。
收到 review(receiving-code-review):技術嚴謹地驗證每條建議,不盲從、不為了討好而照單全收;真有道理才改。

P6finishing-a-development-branch GATE

何時:實作完成、準備整合。

收尾流程:① 先驗測試 → ② 偵測環境(普通 repo / worktree / detached HEAD)→ ③ 決定 base 分支 → ④ 給出固定選項 → ⑤ 執行選擇 → ⑥ 清理工作區。
GATE 測試未全綠不得 merge / 開 PR;丟棄工作需打字確認;只有「本地 merge」與「丟棄」會清 worktree,且只清自己建立的(harness 建的不動)。
四個固定選項(detached HEAD 則為 3 個,無本地 merge)
  1. 本地 merge 回 base 分支(merge 成功並驗測試後,才移除 worktree、刪分支)
  2. 推送並開 PR(保留 worktree 供 PR 迭代,不清理)
  3. 保留分支現狀(自行處理)
  4. 丟棄此工作(需打字 discard 確認)

貫穿全程：鐵律與隨身 skill

這些不是某一階段的步驟,而是整條流程隨時適用的規則。

C1using-superpowers 隨身

動手前先判斷有沒有適用的 skill——只要有 ≥1% 機率適用就先叫出來看。流程類 skill(brainstorming / debugging)先於實作類。使用者明確指示優先於 skill。

C2test-driven-development 鐵律

Iron Law:沒有「先失敗的測試」,就沒有 production code。先寫程式才補測試 → 刪掉重來(不留作參考、不邊看邊抄)。循環:RED(寫失敗測試)→ 看它確實失敗且原因正確 → GREEN(最小實作)→ 看它通過且其他測試仍綠 → REFACTOR(保持綠)。
例外(需經使用者同意):拋棄式原型、產生的程式、設定檔。

C3verification-before-completion 鐵律

Iron Law:沒有「當下這則訊息裡跑出的驗證證據」,不得宣稱完成 / 修好 / 通過。宣稱前先:辨識能證明該主張的指令 → 完整跑一次 → 讀完整輸出與 exit code → 確認後才下結論。出現「應該、大概、似乎」或先說「Done / Perfect」都是紅旗。

C4systematic-debugging 隨身

遇到 bug / 測試失敗 / 非預期行為,先系統化重現再修,別急著套 fix。找到 bug 先寫一個能重現它的失敗測試,再走 TDD 循環——測試同時證明修好且防回歸。
