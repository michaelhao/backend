role-management Specification

角色 CRUD 與自製權限系統（attribute-based middleware、session 權限快取、即時撤銷）的完整行為規格
威脅模型：內部後台、非公網暴露；能登入後台者即為受信任的內部人員——自我提權防護與操作稽核 log 刻意不做。

角色 CRUD

R1角色列表

系統 SHALL 在 GET /roles（需 Role.index 權限）顯示所有角色，每筆 SHALL 含名稱、說明、預設頁面的人類可讀說明（由 permission description 對照）、權限數與使用者數（withCount）。
有權限者可見角色列表PermissionTest::permission_session_reloads_when_role_updated_at_advances（前半）
GIVEN持有 Role.index 權限的使用者
WHENGET /roles
THEN系統回應 200 並渲染角色列表（含權限數與使用者數）

R2新增角色

POST /roles（需 Role.create 權限）SHALL 以 RoleRequest 驗證：name 必填、最長 100 字元且不得與既有角色重複；description 選填、最長 255 字元；default_route 必填且須存在於 permissions.name；permissions 必填陣列、至少 1 項且每項須為存在的 permission id。角色建立與權限同步 SHALL 在單一 database transaction 內完成。成功 SHALL 302 導向 /roles 並帶 success flash「角色已建立」。
成功建立角色PermissionTest::role_crud_create
GIVEN持有 Role.create 權限的使用者
WHENPOST /roles 帶合法的 name、default_route 與 permissions
THEN系統回應 302 導向 /roles
AND角色已存在於資料庫
缺少必填欄位PermissionTest::store_role_fails_with_missing_fields
WHENPOST /roles 不帶任何欄位
THENsession errors 包含 name、default_route 與 permissions
角色名稱重複PermissionTest::store_role_fails_with_duplicate_name
GIVEN已存在名為 Admin 的角色
WHENPOST /roles 帶 name=Admin
THENsession errors 包含 name
permissions 含不存在的 idPermissionTest::store_role_fails_with_nonexistent_permission_id
WHENPOST /roles 的 permissions 陣列含不存在的 permission id
THENsession errors 包含 permissions.0
AND角色未被建立
default_route 不存在於 permissionsPermissionTest::store_role_fails_with_invalid_default_route
WHENPOST /roles 帶不存在的 default_route
THENsession errors 包含 default_route

R5編輯角色

GET /roles/{id}/edit 與 PUT /roles/{id}（皆需 Role.update 權限）SHALL 提供角色編輯。驗證規則同新增（name unique 排除自身）。更新與權限同步 SHALL 在單一 database transaction 內完成。id 不存在時 SHALL 302 導向 /roles 並帶 error flash「找不到該角色」（redirect-with-flash UX，刻意不採 route model binding 的 404）。
成功更新角色PermissionTest::role_crud_update
GIVEN持有 Role.update 權限的使用者與既有角色
WHENPUT /roles/{id} 帶合法欄位
THEN系統回應 302 導向 /roles
AND角色資料已更新
編輯不存在的角色PermissionTest::edit_nonexistent_role_redirects_with_error
WHENGET /roles/99999/edit
THEN系統回應 302 導向 /roles
ANDsession 含 error flash「找不到該角色」
更新不存在的角色PermissionTest::update_nonexistent_role_redirects_with_error
WHENPUT /roles/99999 帶合法欄位
THEN系統回應 302 導向 /roles
ANDsession 含 error flash「找不到該角色」

R6刪除角色

DELETE /roles/{id}（需 Role.delete 權限，前端以 axios 呼叫）SHALL 回應 JSON。成功時 SHALL 於單一 database transaction 內先清除 role_has_permissions pivot 再刪除角色，回應 200 與訊息「角色已刪除」。角色仍有使用者時 SHALL 拒絕並回應 422 與訊息「此角色仍有使用者，無法刪除」。id 不存在時回應 422 與訊息「找不到該角色」。
「找不到該角色」與業務拒絕同為 422——2026-06-12 設計 review 裁示維持現狀、不改 404。
成功刪除角色PermissionTest::role_crud_delete
GIVEN無使用者的角色
WHENDELETE /roles/{id}
THEN系統回應 200 JSON「角色已刪除」
AND角色已自資料庫移除
刪除後 pivot 清空PermissionTest::delete_role_removes_pivot_rows
GIVEN擁有權限關聯的角色
WHENDELETE /roles/{id} 成功
THENrole_has_permissions 不再有該角色的關聯列
仍有使用者的角色拒絕刪除PermissionTest::cannot_delete_role_with_users
GIVEN仍有使用者隸屬的角色
WHENDELETE /roles/{id}
THEN系統回應 422 JSON「此角色仍有使用者，無法刪除」
AND角色仍存在於資料庫
刪除不存在的角色PermissionTest::destroy_nonexistent_role_returns_422
WHENDELETE /roles/99999
THEN系統回應 422 JSON「找不到該角色」

default_route

角色的預設頁面：無權限時的導向目標。permission 存在於 DB ≠ controller method 仍存在，故須雙重驗證。

R3default_route 須可解析至命名路由

default_route 除 exists:permissions,name 外，系統 SHALL 以 PermissionRouteResolver 驗證該 permission 能解析到實際存在的命名路由——若不驗證，refactor 後使用者會被導向不存在的頁面而卡死。
無對應路由的 permission 被拒PermissionTest::role_request_rejects_default_route_without_named_route
GIVEN一個存在於 permissions 但無對應命名路由的 permission
WHENPOST /roles 將其設為 default_route
THENsession errors 包含 default_route（「所選的預設頁面尚未對應到任何路由。」）

R4default_route 權限自動補入

建立或更新角色時，系統 SHALL 自動將 default_route 對應的 permission 加入該角色的權限清單（即使表單未勾選），確保角色一定擁有其預設頁面的存取權。
Service 層自動補入設計，取代舊版「驗證 permissions 須包含 default_route」的拒絕式設計——對使用者更友善且不可能繞過。
建立時自動補入PermissionTest::default_route_permission_is_auto_included_on_store
WHENPOST /roles 的 permissions 未包含 default_route 對應的 permission
THEN建立後該角色仍擁有 default_route 對應的 permission
更新時自動補入PermissionTest::default_route_permission_is_auto_included_on_update
GIVEN既有角色
WHENPUT /roles/{id} 的 permissions 未包含 default_route 對應的 permission
THEN更新後該角色仍擁有 default_route 對應的 permission

權限檢查

權限檢查集中於 CheckPermission middleware 單一入口；權限以 session 快取，異動以版本戳即時撤銷。

R7權限解析

CheckPermission middleware SHALL 依下列順序解析 route 所需權限：(1) controller method 上的 #[RequiresPermission] attribute（優先，CRUD aliases 如 store→Role.create、edit→Role.update 以此明確宣告）、(2) fallback 以 {Module}.{method} 自動推導（controller 類名去除 Controller 後綴）。closure route 無 controller 可解析，SHALL 一律 403。
attribute 宣告的權限生效PermissionTest::admin_can_access_routes_that_viewer_cannot
GIVEN持有 Role.create 權限的使用者
WHENGET /roles/create（#[RequiresPermission('Role.create')]）
THEN系統回應 200
自動推導 fallbackPermissionTest::middleware_auto_infers_permission_from_controller
GIVEN持有 Dashboard.index 權限的使用者
WHENGET /（DashboardController@index → 推導為 Dashboard.index）
THEN系統回應 200
closure route 一律 403PermissionTest::closure_route_in_permission_group_returns_403
GIVEN已登入的 Admin 使用者
WHENGET 一個掛在 permission middleware 內的 closure route
THEN系統回應 403

R8權限不足導向

受 permission middleware 保護的 route：使用者無角色（role_id 為 null）時 SHALL 302 導向 no-role 提示頁；有角色但無該權限時 SHALL 302 導向其角色 default_route 對應的頁面；當 default_route 即為當前所需權限、或無法解析至命名路由時 SHALL 403。寫入操作（POST/PUT/DELETE）SHALL 受與讀取相同的權限檢查。
無角色使用者PermissionTest::user_without_role_is_redirected_to_no_role_page
GIVENrole_id 為 null 的使用者
WHENGET /
THEN系統回應 302 導向 no-role 提示頁
無權限導向預設頁PermissionTest::user_without_permission_is_redirected_to_default_route
GIVEN僅持有 Dashboard.index 的使用者（default_route 為 Dashboard.index）
WHENGET /roles
THEN系統回應 302 導向 /
Viewer 存取非 index 頁被導走PermissionTest::viewer_is_redirected_when_accessing_non_index_pages
GIVENViewer 角色（僅 index 權限）
WHENGET /roles/create
THEN系統回應 302（導向 default_route）
default_route 即當前權限時 403PermissionTest::abort_403_when_default_route_equals_current_permission
GIVEN角色 default_route 為 Role.index 但未擁有該權限
WHENGET /roles
THEN系統回應 403
寫入操作同樣被擋PermissionTest::viewer_cannot_perform_role_write_operations
GIVENViewer 角色（無 Role.create / Role.update / Role.delete）
WHENPOST /roles、PUT /roles/{id}、DELETE /roles/{id}
THEN三者皆 302 導向 default_route
AND資料庫無任何變更

R9Session 權限快取與即時撤銷

使用者權限 SHALL 快取於 session（auth.permissions），權限檢查不查 DB。系統 SHALL 以版本戳 max(users.updated_at, roles.updated_at)（直接走 DB 查詢，不依賴 Eloquent 屬性快取）偵測異動：角色權限被同步時 RoleRepository::syncPermissions() SHALL touch 該角色；middleware 偵測 session 版本戳 stale 時 SHALL 自動 reload 權限，使管理者的異動於受影響使用者下一次 request 生效，無需重新登入。
已知限制：未掛 permission middleware 的場景（如 layout sidebar）依賴登入時載入的 session，stale 至下一次進入 protected route 才修正。
角色權限被拔即時生效PermissionTest::permission_session_reloads_when_role_updated_at_advances
GIVEN已登入且可存取 /roles 的使用者
WHEN管理者移除其角色的 Role.index 權限（觸發 roles.updated_at 前進）後，該使用者再次 GET /roles
THEN同一 session 即被 302 導向 default_route，無需重新登入
使用者被換角色即時生效PermissionTest::permission_session_reloads_when_user_role_id_changes
GIVEN已登入的 Admin 使用者
WHEN管理者將其 role_id 改為僅有 Dashboard.index 的角色後，該使用者再次 GET /roles
THEN同一 session 即被 302 導向 default_route

UI 與 Seeder

R10UI 權限顯示控制

Blade SHALL 以 <x-permission name="Module.action"> component 控制 UI 元素顯示：僅在登入者擁有該權限（session 快取判斷）時渲染 slot 內容。角色列表的「新增角色」「編輯」「刪除」入口 SHALL 分別以 Role.create / Role.update / Role.delete 包裹。
無權限隱藏操作入口無直接測試 — 目視確認 roles/index.blade.php
GIVENViewer 角色（僅 index 權限）
WHEN檢視角色列表頁
THEN不渲染「新增角色」「編輯」「刪除」入口（視圖層行為，由 blade template 保證）

R11權限與預設角色 Seeder

PermissionSeeder SHALL 以宣告式 $modules 陣列定義全部 Module.Action 權限並可重複執行（updateOrCreate）：不在清單中的 orphan permissions SHALL 被移除（含 pivot detach）；SHALL 建立 Admin（全部權限）與 Viewer（僅 index 權限）預設角色（firstOrCreate），且兩者的 default_route 對應權限 SHALL 被包含，對應 permission 不存在時 SHALL 拋出例外。
重複執行 seeder 收斂間接覆蓋 — 每個測試案例皆執行 seedPermissions()
GIVEN已執行過 seeder 的資料庫
WHEN再次執行 PermissionSeeder
THEN權限不重複建立、orphan permissions 被移除、Admin/Viewer 權限被重新同步

刻意設計（不是缺漏）

以下為依威脅模型刻意排除的功能，避免後人誤判為待補項目。

R12無自我提權防護（刻意設計）

系統 MUST NOT 阻擋持有 Role.update 權限的使用者編輯自身所屬角色的權限（含 User.update 持有者調整自身 role_id）。此為刻意設計：內部後台、非公網暴露，能登入後台者即為受信任的內部人員（2026-05 角色安全審查裁定，原 spec/15-role-security-review.md）。同理 MUST NOT 引入 is_system 系統角色保護旗標。
持有 Role.update 者可編輯自身角色無直接測試 — 設計裁定（原 spec/15）
GIVEN持有 Role.update 權限的使用者
WHENPUT /roles/{id} 編輯自身所屬角色的權限
THEN系統正常接受，不做額外阻擋

R13不引入外部權限／稽核套件（刻意設計）

權限系統 MUST NOT 引入 spatie/laravel-permission 等外部權限套件（專案規模小、單一 guard、單一角色，自建 3 張表已足夠），MUST NOT 引入 spatie/laravel-activitylog 等操作稽核機制（內部後台暫無追溯需求，2026-05 安全審查裁定），權限檢查 MUST NOT 使用 Gate::before（檢查集中於 CheckPermission middleware 單一入口）。
composer 依賴不含權限/稽核套件無直接測試 — 目視確認 composer.json
WHEN檢視 composer.json
THEN不存在 spatie/laravel-permission 與 spatie/laravel-activitylog 依賴

—刻意不做的事（彙整）

自我提權防護能登入後台者即為受信任的內部人員；含 is_system 角色保護旗標（R12）
操作稽核 log內部後台暫無追溯需求，不引入 spatie/laravel-activitylog（R13）
外部權限套件單一 guard、單一角色，自建 3 張表已足夠，不引入 spatie/laravel-permission（R13）
users.role_id FK 約束列為後續可做（原 spec/15 P2）；刪除保護以 hasUsers() 檢查實現（R6）
