真實實作 — app/Services/ChatService.php ::sendMessage()

public function sendMessage(int $conversationId, int $senderId, string $body): ChatMessage
{
    $conversation = $this->assertParticipant($conversationId, $senderId);

    $message = DB::transaction(function () use ($conversation, $senderId, $body): ChatMessage {
        $message = $this->messageRepository->create([
            'conversation_id' => $conversation->id,
            'sender_id' => $senderId,
            'body' => $body,
        ]);
        $this->conversationRepository->touchLastMessage($conversation, $message);

        return $message;
    });

    event(new MessageSent($message->load('sender:id,name'), $conversation->otherUserId($senderId)));

    return $message;
}

為什麼用交易? 「寫訊息」與「更新對話摘要(last_message_*)」必須同生同滅。若只寫了訊息卻沒更新摘要,對話清單會顯示過期的最後一句、排序也錯位。交易把兩個寫入綁成原子操作。

為什麼鑑權只看兩個欄位? 對話是 canonical pair,參與者恆等於 user_one_id / user_two_id。直接比這兩欄即可判斷,省掉一次查 participants 表。對話不存在時 findOrFail 丟 ModelNotFoundException(Laravel 轉 404);存在但非參與者丟 ChatOperationException(Controller 轉 403)。

設計取捨:同步廣播 vs 入隊

現況:ShouldBroadcastNow(同步)

  • 時機:在 request 生命週期內同步打 Reverb,不進佇列。
  • 優點:訊息即時到達;部署簡單,不需要跑 queue worker。
  • 代價:Reverb 若慢,會拖長這個 HTTP response 時間。
  • 適配:後台內部使用、量不大,延遲可接受。

替代:ShouldBroadcast(入隊)

  • 時機:event 進佇列,背景 worker 派發廣播。
  • 優點:response 立刻回、與廣播解耦。
  • 代價:必須維運 queue worker;廣播可能稍延遲。
  • 何時換:廣播對象變多、或 Reverb 往返變慢時。

B. 發起 / 取得對話

POST /chats/start。點選一位使用者開始聊天:已存在就取回、不存在就建立。重點在 canonical pair 與併發容錯。

層method做什麼
Controllerstart(StartConversationRequest)驗證 target_user_id(exists:users 且不得為自己);捕捉例外 → 422;回 conversation_id
ServicegetOrCreateConversation(int $userId, int $targetUserId)擋自我對話 → findPair 找既有 → 沒有就 createWithParticipants
RepositoryfindPair($a, $b)先 orderPair 規範成 [min, max],再以兩欄查唯一對話
RepositorycreateWithParticipants($a, $b)交易內 create 對話 + participants()->createMany 兩筆參與者

真實實作 — app/Services/ChatService.php ::getOrCreateConversation()

public function getOrCreateConversation(int $userId, int $targetUserId): ChatConversation
{
    if ($userId === $targetUserId) {
        throw new ChatOperationException('無法與自己建立對話');
    }

    $existing = $this->conversationRepository->findPair($userId, $targetUserId);
    if ($existing) {
        return $existing;
    }

    try {
        return $this->conversationRepository->createWithParticipants($userId, $targetUserId);
    } catch (QueryException $e) {
        // 並發下另一請求已建立同一對話（撞 unique index）→ 取回既有的，而非回 500
        $conversation = $this->conversationRepository->findPair($userId, $targetUserId);
        if (! $conversation) {
            throw $e;
        }

        return $conversation;
    }
}

為什麼要 canonical pair? orderPair() 永遠把較小的 id 放 user_one_id、較大的放 user_two_id($a < $b ? [$a,$b] : [$b,$a])。配合 (user_one_id, user_two_id) 唯一索引,(A,B) 與 (B,A) 必然落在同一列,從根本杜絕「同一對人有兩個對話」。

坑點 兩人同時點對方,誰先誰後?(併發建立)

現象:A、B 幾乎同時送出 start,兩個請求都 findPair 撲空、都嘗試 createWithParticipants。

機制:唯一索引讓第二個 INSERT 拋 QueryException。Service catch 後重新 findPair,取回第一個請求剛建好的那筆並正常回傳,而不是回 500。

為什麼這樣設計:本專案三張 chat_* 表沒有 DB 外鍵,改以「唯一索引 + 應用層容錯」保證一致性。這是刻意的取捨(見資料層)。

C. 讀對話清單 / 訊息分頁

首屏 index 與 conversations 走同一條清單鏈;messages 走訊息分頁鏈。重點在避免 N+1 與游標分頁。

C-1 對話清單(含未讀數)

層method做什麼
Controllerindex() / conversations()index 回 View(順帶塞可選使用者);conversations 回 JSON。兩者都呼叫 listConversations
ServicelistConversations(int $userId): array先一次取得所有對話的未讀數,再組裝每筆對話的 other_user / last_message / unread_count
RepositoryChatMessageRepository::unreadCountsByConversation($userId)一次 JOIN + GROUP BY 算出 {conversation_id => 未讀數}
RepositoryChatConversationRepository::forUser($userId)查使用者的對話,with(['userOne:id,name','userTwo:id,name','lastMessage']) eager load,依 last_message_at 倒序

為什麼未讀數要批次算? 若在組裝迴圈裡逐對話查未讀,N 個對話就 N 次查詢(N+1)。改用一次 JOIN 聚合,把整個使用者的未讀一次撈齊,再用陣列查表。

逐對話查(N+1,未採用)

  • 每筆對話呼叫一次 unreadCountFor()。
  • 20 個對話 = 20 次 COUNT 查詢。

一次 JOIN GROUP BY(現況)

  • unreadCountsByConversation() 單次查詢。
  • JOIN participants 取 last_read_at,排除自己送的,GROUP BY conversation_id。

坑點 eager load 一律用 userOne:id,name 限定欄位,避免把 users 整列(含敏感欄位)序列化進 JSON。另外,若對方使用者已被刪除(無外鍵),listConversations 會把該孤兒對話 return null 再 filter() 掉,避免存取 null 而 500。

C-2 訊息分頁(游標)

層method做什麼
Controllermessages(int $conversation)讀 query before_id(空則 null);捕捉例外 → 403;回 messages
ServicegetMessages($conversationId, $userId, ?$beforeId)先 assertParticipant 鑑權,再分頁
RepositorypaginateForConversation($conversationId, ?$beforeId, $perPage = 30)where('id','<',$beforeId)(向上捲動載更舊)、orderByDesc('id')、limit(30)、with('sender:id,name')

為什麼用 before_id 游標而非 offset 分頁? 聊天會持續有新訊息插入,offset 分頁會在資料位移時重複或漏抓。用「比某個 id 更小」的游標,翻頁結果穩定,且能吃 (conversation_id, id) 複合索引。前端取回後反轉成由舊到新顯示。

D. 已讀與未讀計數

PATCH /chats/{conversation}/read 與 GET /chats/unread-count。未讀數不落欄位,完全靠 last_read_at 即時算。

層method做什麼
ControllermarkRead(int $conversation)呼叫 markAsRead,回最新全域未讀數
ServicemarkAsRead($conversationId, $userId): int鑑權 → 更新該參與者 last_read_at → 重算全域未讀並回傳
RepositoryChatConversationParticipantRepository::markRead($conversationId, $userId)UPDATE ... SET last_read_at = now()
ServicetotalUnread($userId): int代理到 ChatMessageRepository::totalUnreadFor
RepositorytotalUnreadFor($userId): intarray_sum(unreadCountsByConversation($userId))

為什麼未讀數不存欄位? 「未讀」= 對方送的、且 created_at 晚於我的 last_read_at 的訊息數。只要每次進對話更新一個 last_read_at 時間戳,任何時刻都能即時算出未讀,不必在每次收訊時去維護一個容易飄掉的計數欄位(多分頁、競態下尤其安全)。

為什麼 totalUnreadFor 複用 unreadCountsByConversation? 「全域未讀」就是「各對話未讀」的加總。複用同一份 SQL 定義,避免兩處各寫一遍 WHERE 條件、日後改了一處另一處走樣。

真實實作 — ChatMessageRepository::unreadCountsByConversation()

return ChatMessage::query()
    ->join('chat_conversation_participants as p', function ($join) use ($userId) {
        $join->on('p.conversation_id', '=', 'chat_messages.conversation_id')
            ->where('p.user_id', '=', $userId);
    })
    ->where('chat_messages.sender_id', '!=', $userId)
    ->where(function ($query) {
        $query->whereNull('p.last_read_at')
            ->orWhereColumn('chat_messages.created_at', '>', 'p.last_read_at');
    })
    ->groupBy('chat_messages.conversation_id')
    ->selectRaw('chat_messages.conversation_id as conversation_id, COUNT(*) as aggregate')
    ->pluck('aggregate', 'conversation_id')
    ->map(fn ($count) => (int) $count)
    ->all();

即時傳輸:廣播事件與頻道授權

送出鏈最後的 event(MessageSent) 如何變成對方螢幕上的新訊息。傳輸層用 Laravel Reverb(自架 WebSocket,走 Pusher 協定)。

MessageSent 事件

成員內容用途
implements ShouldBroadcastNow同步、不入隊request 內直接扇出
broadcastOn()兩個 PrivateChannel:chat.user.{recipientId} 與 chat.user.{senderId}通知接收者;同時通知寄件者自己(讓他其他分頁/裝置也同步)

為什麼也廣播給寄件者自己? 寄件者可能同時開了多個分頁/裝置。把訊息也送回 chat.user.{senderId},其他分頁就能即時看到剛送出的訊息。本來送出那個分頁靠樂觀渲染已經先顯示了,所以前端用訊息 id 去重避免重複(見下節)。

const { echo, userId } = useEcho();

if (echo) {
    echo.private(`chat.user.${userId}`).listen('.message.sent', (event) => {
        // 廣播給聊天頁處理（若該頁開著）

為什麼 badge 一律回伺服器抓,而不本地 +1? 多分頁、競態下本地累加容易飄。每次都向伺服器要「權威」未讀數(unread-count 端點),數字才不會錯。這也是為什麼即使沒有 Echo,進任一頁都會 refreshChatBadge() 至少更新一次。

坑點 無 Echo 時的降級行為

useEcho 在未登入、或缺 VITE_REVERB_APP_KEY / meta[user-id] 為空時回 { echo: null }。此時:沒有即時推送,但 HTTP 路徑(送訊、載訊息、標已讀、抓未讀)全部照常運作,只是新訊息要靠重新整理 / 重載清單才看到。聊天功能不會整個壞掉,只是退化成非即時。

另一個防呆:meta.content 為空字串時 Number('')=0 會誤訂到 chat.user.0,故程式碼明確把空字串視為未登入直接退出。

樂觀送出與去重(settle)

送出鏈在前端的對應:按下送出立刻顯示「傳送中」,不等伺服器。但這帶來「同一則訊息可能來兩次」的去重問題。

一則訊息在前端的生命週期

POST

到 renderedMessageIds
settle('sent')泡泡轉為已送出
同時

兩個訊息來源會抵達送出者的畫面:① POST 的 201 response;② chat.user.{senderId} 自身廣播。前端在收到 201 時把 message.id 記進 renderedMessageIds;之後廣播帶著同一個 id 回來時就被去重丟棄,不會重複顯示。

坑點 送出失敗 → settle('failed') 與重試

sendBody 先樂觀 push 一個 pending 泡泡並 forceScrollBottom();POST 成功 → settle('sent');失敗 → settle('failed', retry) 掛上重試 callback(移除舊泡泡並重送)。pending.settled 旗標確保一個 pending 只結算一次,避免 response 與例外路徑重複處理。

index(user_id)未讀聚合 JOIN 以 user_id 過濾D unreadCountsByConversation

為什麼參與者要獨立成一張表? 對話本身只記「是哪兩個人」;但「每個人各自的已讀進度(last_read_at)」是 per-user 狀態,放在 participants 表,建立對話時一次寫兩筆(createMany)。未讀計算就靠 JOIN 這張表的 last_read_at 與訊息 created_at 比對。
