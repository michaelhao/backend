一、聊天完整流程(Workflow)

送訊主流程(含失敗分支)。注意:即時送達靠 WebSocket 廣播,但「真相來源」是 DB —— 先寫入後廣播。

1. 發起對話

  • 聊天頁右上下拉選單選一位使用者 → 前端 POST /chats/start { target_user_id }。
  • 後端 getOrCreateConversation():擋「與自己對話」→ 以 canonical pair(較小 id 放 user_one_id、較大放 user_two_id)找既有或建立,回 conversation_id。
  • 建立時同時寫入兩筆 chat_conversation_participants(兩位使用者各一)。

2. 送出訊息(樂觀更新)

  • 前端先在本地 立即渲染一個「傳送中…」泡泡(不等伺服器),推入 pendingSends[] 追蹤。
  • 同時 POST /chats/{conversation}/messages { body }。body 驗證:必填、字串、max:5000。
  • 後端 sendMessage() 先 assertParticipant() 鑑權,再於 交易內寫訊息 + 更新對話摘要,提交後派發 MessageSent 事件。

3. 廣播與接收

  • MessageSent 為 ShouldBroadcastNow(同步、不進 queue),廣播到兩個私有頻道:接收者 chat.user.{recipientId} 與送出者自己 chat.user.{senderId}(讓送出者其他分頁/裝置同步)。
  • 接收端 bootstrap.js 在 chat.user.{我} 收到 .message.sent → 派發 chat:message 自訂事件 + 刷新未讀 badge。
  • 聊天頁監聽 chat:message:若是當前開啟的對話 → appendMessage() 並立即 PATCH 已讀;否則僅排程重載列表。

4. 已讀 / 未讀

  • 開啟對話或收到當前對話新訊息 → PATCH /chats/{conversation}/read,後端把該使用者的 chat_conversation_participants.last_read_at 設為 now()。
  • 未讀數不落欄位,而是即時用「last_read_at 之後、非自己送的訊息」計算(見 6-2)。
  • 全站未讀 badge 一律向 GET /chats/unread-count 抓權威數字,避免多分頁本地累加飄掉。

5. 儲存與顯示

  • 訊息永久存於 chat_messages;對話列上的「最後訊息/時間」由 chat_conversations.last_message_id / last_message_at 反正規化保存(送訊時 touchLastMessage() 更新)。
  • 開對話 GET /chats/{conversation}/messages 以 cursor 分頁(before_id、每頁 30、id 由新到舊)取回,前端反轉成由舊到新渲染。
  • 渲染:依日期插入分隔線、同一寄件者連續訊息分組、貼底才自動捲動(否則顯示「新訊息」浮標);訊息一律 textContent 跳脫,杜絕 XSS。

二、技術選型與運作機制

技術棧與各自角色

  • Laravel Reverb:Laravel 第一方 WebSocket 伺服器,相容 Pusher 協定。.env BROADCAST_CONNECTION=reverb + REVERB_*;前端用 VITE_REVERB_*。
  • Laravel Echo + pusher-js:前端訂閱私有/presence 頻道。.private() 收訊息、.whisper()/.listenForWhisper() 做「輸入中」、.join() 做線上狀態。
  • 後端事件廣播:event(new MessageSent(...)) → Reverb 扇出。授權在 routes/channels.php。
  • Axios:所有非即時操作(載入、送出、已讀、未讀數)走一般 HTTP JSON API。

為何是 WebSocket 而不是 Polling

機制本專案是否採用說明
HTTP 短輪詢(setInterval 打 API)未採用程式碼中沒有定時輪詢訊息;不會每幾秒打一次 API
WebSocket(Reverb + Echo)採用持久連線即時推送 .message.sent、typing、presence
純同步 HTTP部分載入/送出/已讀走 HTTP;但「即時收訊」靠廣播,非請求輪詢

對話列表的刷新也不是輪詢:收到廣播事件後以 scheduleListReload()(300ms debounce)收斂成一次重載,避免每則訊息都整包重抓。

無 Echo 時的降級行為

bootstrap.js 只有在 VITE_REVERB_APP_KEY 與 meta[name="user-id"] 都存在時才初始化 window.Echo;聊天頁的即時功能也都包在 if (window.Echo) 內。因此未設定 Reverb 時頁面仍可運作:

  • ✅ 仍可:載入對話/歷史、送訊息(POST)、標已讀、未讀 badge(進頁面抓一次)。
  • ❌ 失去:即時收新訊息(需重新整理)、輸入中提示、線上狀態、跨分頁同步。

關聯拓撲

  • User ↔ Conversation:透過 user_one_id / user_two_id 兩個 belongsTo。對話正規化成 canonical min/max pair,等同一對一對話的唯一化(非傳統 M2M pivot)。
  • Conversation 1—∗ Message(hasMany messages);另有 belongsTo lastMessage 指反正規化的最後一則。
  • Conversation 1—∗ Participant(hasMany participants,恰 2 筆)。participants 表本質是「每位使用者在此對話的已讀回條」,不是傳統多對多中介表。
  • Model 方法:ChatConversation::otherUserId($userId) 由 pair 推出對方 id;User::chatParticipants() hasMany。

核心 API 邏輯

  • 對話列表 listConversations():先取批次未讀 map,再取對話(eager userOne/userTwo/lastMessage),map 成輸出;對方已被刪除(無 FK)時回 null 並 filter() 掉,避免存取 null 而 500。
  • 建立對話 getOrCreateConversation():擋自我對話 → findPair → 不存在則 createWithParticipants();併發撞 unique 時 catch 後重新 findPair(見 6-3)。
  • 取歷史 getMessages():先 assertParticipant() 再 paginateForConversation()(cursor)。
  • 送訊息 sendMessage():鑑權 → 交易(寫訊息 + touchLastMessage)→ 廣播(見 6-1)。
  • 標已讀 markAsRead():鑑權 → 更新 last_read_at → 回 totalUnread()。

N+1 與 Eager Loading 評估 ✓ 無 N+1

操作查詢數預載入
對話列表2(未讀批次 1 + 對話 1)with(['userOne:id,name','userTwo:id,name','lastMessage'])
歷史訊息1with('sender:id,name')
未讀計數1(JOIN + GROUP BY 批次)不需,單一聚合查詢

對話列表 — 一次預載入避免逐列查使用者 · app/Repositories/ChatConversationRepository.php

ChatConversation::with(['userOne:id,name', 'userTwo:id,name', 'lastMessage'])
    ->where(fn ($q) => $q->where('user_one_id', $userId)->orWhere('user_two_id', $userId))
    ->orderByDesc('last_message_at')
    ->get();

未讀數採單次批次查詢回 [conversationId => 未讀數],而非每個對話各查一次(那才會 N+1)。totalUnreadFor() 直接 array_sum() 同一份結果,兩處未讀定義共用,不會走樣。

交易與一致性 ✓ 有用 DB::transaction

  • 送訊息:寫 chat_messages + 更新對話 last_message_* 包在同一 DB::transaction —— 全有或全無,不會出現「有訊息但對話摘要沒更新」。
  • 建立對話:createWithParticipants() 把對話 + 兩筆參與者包在交易內。
  • 廣播時機:event() 在交易提交後才派發,確保推播出去的訊息一定已落地 DB。

三層授權

  • 路由層:permission 中介層 + #[RequiresPermission('Chat.index')]。
  • 業務層:assertParticipant() = findOrFail(不存在 404)+ 比對 user_one_id/user_two_id(非參與者丟 ChatOperationException → 403)。直接用對話自身欄位判斷,省一次 participants 查詢。
  • 頻道層:routes/channels.php 對 chat.user.{id}(本人)、chat.conversation.{id}(isParticipant)、chat.online(presence)做授權。

五、傳輸機制與前後端協作

頻道與廣播事件

  • MessageSent implements ShouldBroadcastNow —— 同步廣播(不進 queue),在送訊 request 內直接打 Reverb。
  • broadcastOn() 回兩個 PrivateChannel:chat.user.{recipientId} 與 chat.user.{senderId}(送出者多裝置同步,前端再以訊息 id 去重)。
  • broadcastAs() = message.sent;broadcastWith() 帶 id, conversation_id, sender_id, sender_name, body, created_at。
  • 對話頻道 chat.conversation.{id} 只承載「輸入中」whisper(訊息本身走個人頻道)。

頻道授權 · routes/channels.php

// 私有頻道：個人頻道，承載 message.sent
Broadcast::channel('chat.user.{userId}', function ($user, int $userId) {
    return (int) $user->id === $userId;
});

// 私有頻道：對話頻道，僅承載「輸入中」whisper；參與者判斷重用 repository
Broadcast::channel('chat.conversation.{conversationId}', function ($user, int $conversationId) {
    return app(ChatConversationRepository::class)->isParticipant($conversationId, (int) $user->id);
});

// Presence 頻道：全後台線上狀態
Broadcast::channel('chat.online', function ($user) {
    return ['id' => $user->id, 'name' => $user->name];
});

六、關鍵核心實作(真實程式碼)

以下皆為專案實際程式碼節錄,非示意。

6-1. 送訊:交易內寫入 + 交易後廣播

app/Services/ChatService.php

public function sendMessage(int $conversationId, int $senderId, string $body): ChatMessage
{
    // 先驗證 user 為對話參與者，否則丟 ChatOperationException → 403
    $conversation = $this->assertParticipant($conversationId, $senderId);

    // 寫訊息 + 更新對話摘要(last_message_id/at)同屬一筆交易：全有或全無
    $message = DB::transaction(function () use ($conversation, $senderId, $body): ChatMessage {
        $message = $this->messageRepository->create([
            'conversation_id' => $conversation->id,
            'sender_id' => $senderId,
            'body' => $body,
        ]);
        $this->conversationRepository->touchLastMessage($conversation, $message);

        return $message;
    });

    // 交易提交後才廣播：確保推播出去的訊息一定已落地(同步 ShouldBroadcastNow)
    event(new MessageSent($message->load('sender:id,name'), $conversation->otherUserId($senderId)));

    return $message;
}

6-2. 批次未讀計數(避免 N+1 的核心)

app/Repositories/ChatMessageRepository.php

public function unreadCountsByConversation(int $userId): array
{
    return ChatMessage::query()
        // JOIN 參與者表，鎖定「我」在每個對話的 last_read_at
        ->join('chat_conversation_participants as p', function ($join) use ($userId) {
            $join->on('p.conversation_id', '=', 'chat_messages.conversation_id')
                ->where('p.user_id', '=', $userId);
        })
        ->where('chat_messages.sender_id', '!=', $userId)            // 排除自己送的
        ->where(function ($query) {
            $query->whereNull('p.last_read_at')                      // 從未讀過 → 全未讀
                ->orWhereColumn('chat_messages.created_at', '>', 'p.last_read_at');
        })
        ->groupBy('chat_messages.conversation_id')
        ->selectRaw('chat_messages.conversation_id as conversation_id, COUNT(*) as aggregate')
        ->pluck('aggregate', 'conversation_id')                     // [conversationId => 未讀數]
        ->map(fn ($count) => (int) $count)
        ->all();
}

6-3. 並發容錯建立對話

app/Services/ChatService.php

public function getOrCreateConversation(int $userId, int $targetUserId): ChatConversation
{
    if ($userId === $targetUserId) {
        throw new ChatOperationException('無法與自己建立對話');
    }

    $existing = $this->conversationRepository->findPair($userId, $targetUserId); // 順序無關
    if ($existing) {
        return $existing;
    }

    try {
        return $this->conversationRepository->createWithParticipants($userId, $targetUserId);
    } catch (QueryException $e) {
        // 並發下另一請求已先建立同一對話(撞 chat_conv_pair_unique)→ 取回既有，而非回 500
        $conversation = $this->conversationRepository->findPair($userId, $targetUserId);
        if (! $conversation) {
            throw $e;
        }

        return $conversation;
    }
}

6-4. 前端樂觀送出的單一收斂點 settle()

resources/js/chats/index.js

// POST 成功或「自身廣播認領」皆可結算；已結算者不再處理(避免重複送出)
const settle = (pending, status, retry) => {
    if (pending.settled) { return; }
    pending.settled = true;
    const i = pendingSends.indexOf(pending);
    if (i !== -1) { pendingSends.splice(i, 1); }
    setStatus(pending.statusEl, status, retry);
};

const sendBody = async (body) => {
    // …樂觀 append「傳送中…」泡泡、推入 pendingSends…
    try {
        const { data } = await window.axios.post(`/chats/${targetId}/messages`, { body });
        if (data.message?.id != null) { renderedMessageIds.add(data.message.id); } // 廣播回來據此去重
        settle(pending, 'sent');          // 若廣播已先認領，settled=true，這裡會跳過
        scheduleListReload();
    } catch (e) {
        if (pending.settled) { return; }  // 廣播已確認送達 → 只是回應遺失，視為成功(不重送)
        settle(pending, 'failed', () => { pending.row.remove(); sendBody(body); });
    }
};

七、風險評估與建議

直接回答 raised 的工程問題。前提:本系統為後台內部使用、非公網暴露、低併發;以下「建議」多屬「資料量/併發上升時」才需處理。

主題現況影響建議嚴重度
未讀查詢索引 chat_messages.created_at 無索引;未讀靠即時 JOIN+GROUP BY,無反正規化計數 訊息量大時未讀統計逐漸變慢(每次列表/badge 都算) 加 (conversation_id, created_at) 複合索引;量再大可評估反正規化未讀數 中
DB 外鍵缺失 三表皆無 FK 刪 user 不連動、可能留孤兒列;靠應用層 null 容錯 視需求補 FK 或刪除使用者時的級聯清理;目前 listConversations() 已容錯不致 500 中
同步廣播 MessageSent 用 ShouldBroadcastNow 送訊 request 內同步打 Reverb;Reverb 慢時拖長回應 量大可改 ShouldBroadcast(進 queue)縮短回應時間,需有 queue worker 低
last_message 反正規化 last_message_id 非外鍵、手動維護 未來若支援刪訊息,會留 stale 指標 加刪訊息功能時一併維護/重算對話摘要 低
Unique / 重複資料 對話 pair、參與者皆有 UNIQUE — 無需處理(已涵蓋,且併發撞鍵有 Service 收斂) 無
  • N+1:已用 eager loading + 批次未讀查詢妥善處理,無需改。
  • DB 交易:送訊、建立對話皆已正確使用 DB::transaction。
  • Unique:重複對話、重複參與者都有唯一鍵保護,無漏。
  • 索引:內部低併發下夠用;資料量上升時建議補 chat_messages(conversation_id, created_at)。
  • 外鍵:以應用層容錯替代 DB 外鍵,屬刻意取捨,留意刪使用者的孤兒清理。
