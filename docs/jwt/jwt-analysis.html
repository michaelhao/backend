JSON Web Token（JWT）技術分析

無狀態認證權杖的原理、應用場景、優缺點與本專案導入評估
一句話：JWT 是一種自帶簽章、可獨立驗證的緊湊權杖格式（RFC 7519），讓伺服器不必查資料庫或保存 session，僅憑驗章就能信任請求者的身分與宣告。
主題：JSON Web Token 標準：RFC 7519 / 7515(JWS) / 7516(JWE) 文件性質：技術選型分析
本頁為技術選型分析,非實作規格。第 7 節「是否適合導入」的結論依據本專案目前的認證架構現況。

1. 專案核心概述

JWT 是什麼、解決了什麼痛點。

概述自帶簽章的無狀態身分權杖

JWT（JSON Web Token）是一段以 . 分隔成三部分的字串,內含一組 JSON 宣告(claims)與一份數位簽章。伺服器只要用共享密鑰或公鑰驗證簽章,即可確信內容未被竄改,進而信任其中的使用者身分與權限——全程不需查 session 儲存體。

它解決的痛點:傳統 session 認證要求伺服器為每個登入者保存狀態(記憶體 / Redis / 資料庫),在水平擴展(多台無共享記憶體的伺服器)、跨網域(SPA / 行動 App 打不同網域的 API)、跨服務(microservices 互信)情境下,集中式 session 會成為瓶頸與耦合點。JWT 把「身分狀態」放進權杖本身交給用戶端攜帶,伺服器改為無狀態驗章,從而水平擴展與跨域變得簡單。

關鍵心智模型:JWT 的預設保證是「完整性 / 真實性」(簽了章、沒被改),不是機密性。除非額外用 JWE 加密,否則 payload 任何人都能 Base64Url 解開閱讀。

2. 核心功能與特色

最主要的技術亮點。

特色技術亮點

  • 三段式結構 Header.Payload.Signature RFC 7519 三段各自 Base64Url 編碼後以 . 串接;Header 描述演算法、Payload 放宣告、Signature 保護前兩段。
  • 無狀態(stateless)驗證 伺服器只需密鑰/公鑰即可離線驗章,不必查 DB 或集中式 session,天然適合水平擴展。
  • 自帶標準宣告(claims) 內建 iss(簽發者)、sub(主體)、aud(受眾)、exp(到期)、iat(簽發時間)、nbf(生效時間)、jti(唯一 ID),亦可放自訂宣告(角色、權限)。
  • 多種簽章演算法 對稱式 HS256(HMAC,單一密鑰簽與驗);非對稱式 RS256/ES256(私鑰簽、公鑰驗,適合多服務只發公鑰驗章)。
  • 緊湊、URL-safe Base64Url 編碼可安全放進 HTTP header(Authorization: Bearer)、query string 或 cookie。
  • 跨語言、跨平台 JSON + 標準演算法,各語言皆有成熟函式庫,前後端 / 異質服務皆可互通。
  • 可選加密(JWE) 需保護 payload 機密時,可用 JWE(RFC 7516)加密內容;一般認證情境僅用 JWS 簽章即可。

3. 主要應用場景

開發者在什麼情況下應該選擇使用 JWT。

場景適合採用 JWT 的情境

  • SPA / 行動 App 對後端 API 認證 前端(Vue/React/Next、iOS/Android)與 API 不同源、無共享 session 時,以 Authorization: Bearer <jwt> 攜帶身分。
  • 無狀態水平擴展 多台 API 伺服器在負載平衡後方,不想共享 session 儲存;每台各自驗章即可。
  • Microservices 服務間互信 服務 A 簽發、服務 B 用公鑰驗章信任(RS256),免於共享 session 或互查使用者庫。
  • SSO / OAuth 2.0 / OIDC OpenID Connect 的 id_token 本身就是 JWT;單一登入後以權杖在多系統間傳遞身分。
  • 短效、單次用途的授權連結 email 驗證、密碼重設、限時下載等,把意圖與到期時間簽進權杖,免在 DB 另存狀態。
反向判準:若你的前端與後端同源且伺服器本來就保有 session(傳統 MPA / Blade / Inertia),JWT 帶來的「無狀態」優勢用不上,反而增加複雜度——此時 session cookie 通常是更好的選擇。

原理三段如何協作

1) Header:JSON 描述權杖型別與簽章演算法,例如 {"alg":"HS256","typ":"JWT"},Base64Url 編碼成第一段。

2) Payload:JSON 宣告集合(標準 claims + 自訂 claims),Base64Url 編碼成第二段。僅編碼、未加密,不可放機密。

3) Signature:對「base64url(header) + "." + base64url(payload)」用密鑰依 alg 演算法計算簽章,成第三段。任何人改動前兩段都會導致驗章失敗。

驗證:伺服器以相同密鑰(HMAC)或對應公鑰(RSA/ECDSA)重算/驗證簽章,再檢查 exp(未過期)、nbf、aud 等宣告,全部通過才信任。

Access / Refresh 雙權杖是常見實務:access token 短效以縮小被竊風險;refresh token 較長效、存於伺服器可撤銷,用來換發新的 access token——這也是 JWT「無法即時撤銷」缺點的常見緩解手段。

// === 簽發(登入成功後)===
function issueToken(user, secret) {
  header  = { alg: "HS256", typ: "JWT" }
  payload = { sub: user.id, role: user.role,
              iat: now(), exp: now() + 900 }   // 15 分鐘後到期
  data = base64url(header) + "." + base64url(payload)
  sig  = hmacSha256(data, secret)
  return data + "." + base64url(sig)
}

// === 驗證(每次受保護請求)===
function verify(token, secret) {
  [h, p, s] = token.split(".")
  expected  = base64url(hmacSha256(h + "." + p, secret))
  if (s != expected)        throw "簽章無效"   // 被竄改或偽造
  claims = jsonDecode(base64urlDecode(p))
  if (claims.exp < now())   throw "已過期"
  return claims               // 信任 sub / role 做授權
}
Laravel 視角:若本專案真的要做 token 認證,不會自刻上述邏輯,而是用官方套件 laravel/sanctum(個人存取權杖,內建可撤銷)或 laravel/passport(完整 OAuth2,簽發 JWT)。自行實作簽章/驗章/金鑰輪替容易出安全漏洞。

6. 優缺點評估

與同類方案(session cookie、不透明 token)相比的取捨。

優勢

  • 無狀態:伺服器免存 session,水平擴展與無共享部署簡單。
  • 跨域 / 跨服務:用 Authorization header 攜帶,不受 cookie 同源限制;非對稱簽章讓多服務只憑公鑰即可互信。
  • 自帶宣告:角色、權限可直接放進權杖,授權時免再查庫(注意時效)。
  • 標準化、生態成熟:RFC 7519,各語言函式庫齊全,與 OAuth2 / OIDC 無縫接軌。
  • 效能:驗章是本地運算,省去每次請求的 session 查詢。

潛在限制 / 缺點

  • 難以即時撤銷:權杖一旦簽發,在 exp 前都有效;要立即登出/封鎖需額外 blocklist 或短 exp + refresh,反而退回有狀態,抵銷無狀態優勢。
  • payload 非機密:預設只簽不加密,任何人可解碼閱讀,敏感資料不可入內(除非 JWE)。
  • 體積較大:比 session id(一小串)大上許多,每次請求都要傳整個權杖。
  • 用戶端儲存兩難:放 localStorage 怕 XSS 竊取;放 cookie 又得處理 CSRF——沒有完全無痛的選項。
  • 金鑰 / 時鐘管理成本:密鑰輪替、exp 依賴各端時鐘同步,維運複雜度高於 session。
  • 易誤用:alg:none、弱密鑰、不驗 aud 等歷史漏洞,自行實作風險高。

7. 本專案是否適合導入

依本後端目前的認證架構現況評估。

評估結論與理由

結論:目前不建議導入 JWT。本專案是同源、有狀態的 Laravel MPA,既有的 session cookie 認證已完整滿足需求;JWT 的無狀態/跨域優勢在此用不上,導入只會增加複雜度與安全面。
現況事實(探索所得):
純 session-basedconfig/auth.php 僅 web/session guard;無 Sanctum / Passport / JWT 套件。
同源 MPA,非分離式前端Blade 伺服器渲染 + 少量原生 JS;表單傳統 POST + 頁面重載,無獨立 SPA。
無對外 API 層無 routes/api.php;無 SPA / 行動 App / 第三方服務消費此後端。
內部使用、非公網暴露對齊既有威脅模型;正式環境無對外連線,無跨域/跨服務認證需求。
導入成本 > 收益:
需重構 AuthService 的登入流程改為簽發權杖、前端改帶 Authorization header、捨棄 Blade 的 @csrf 模型、權限快取從 session 改為權杖內嵌(失效更難處理)、額外的金鑰管理——而這些全是為了換取本專案用不到的無狀態與跨域能力。
何時才該重新評估:
出現獨立 SPA / 行動 App前端與後端不同源、需打 API 取資料時。
對外開放 API需供第三方或外部系統以權杖存取。
拆分為 microservices服務間需以權杖互信。
屆時的優先選項仍是 Laravel 官方的 laravel/sanctum(多數 SPA / 行動 App 場景足夠且可撤銷)或 laravel/passport(需完整 OAuth2 時),而非自刻 JWT。
