全面以 Vue.js 替換原生 JS — 遷移評估

目標架構:保留 Laravel Blade 渲染,將原生 JS 互動塊改寫為掛在頁面上的 Vue 島嶼(islands)
一句話：技術上可行且風險可控——本專案「每頁一個 @vite entry」的結構與 Vue 島嶼模型天然契合,因此建議採逐島漸進式遷移,而非一次性大改;先以重用元件與中型表單試點,即時聊天頁(最高風險)留到最後。
目標架構：Blade + Vue 3 島嶼 現況:原生 JS 18 檔 / ~2,077 行 文件性質：遷移可行性評估
本頁為遷移評估,非實作計畫,亦非最終導入決策書。盤點數據取自 resources/js/* 與各 *.blade.php 現況。範圍鎖定使用者選定的「Blade + Vue 島嶼」;Inertia 全頁 Vue 與前後端分離 SPA 僅末段一句帶過。

1. 評估結論

先講結論,後面各節是支撐依據。

結論可行,且建議漸進式逐島遷移

結論:全面改用 Vue 是可行的,但不該一次性大改。現有「每頁載入一支專屬 JS、以根節點接管一塊互動」的寫法,正好就是 Vue 島嶼的形狀——把命令式 DOM 操作換成 Vue 的響應式元件即可,Laravel / Blade / 路由 / 認證一概不動。
  • 契合度高18 個 @vite entry → 18 個可獨立遷移的島;一次改一頁、可隨時暫停,不存在「全有或全無」的切換風險。
  • 收益最大處命令式 DOM 操作最重的頁(聊天、帳單表單)正是 Vue 響應式收益最大、可讀性提升最多之處。
  • 主要風險可隔離唯一高風險是 534 行的即時聊天頁;把它排在最後,前面累積經驗、確立島嶼慣例後再動。
  • 不需要 SSR / SPA本系統為內部後台,不在意 SEO;客戶端島嶼(CSR)即足夠,免去 SSR/hydration 的複雜度。

2. 現況盤點

要遷移的東西到底有多少、長什麼樣。

現況統一的「漸進增強」寫法

所有原生 JS 都是同一個模式:Blade 先渲染好 HTML,JS 再以 getElementById 找根節點、讀 data-*、querySelector 子元素、掛事件、切換 class。資料流是「Blade → HTML → JS 讀 DOM」。

// resources/js/components/searchable-select.js（典型樣貌）
function initSearchableSelect(root) {
  const hiddenInput = root.querySelector('input[type="hidden"]')
  const options    = root.querySelectorAll('.ss-option')
  textInput.addEventListener('input', () => { filter(); showDropdown() })
  options.forEach(opt => opt.addEventListener('click', () => {
    hiddenInput.value = opt.dataset.value          // 命令式改 DOM
    opt.classList.add('bg-blue-50')           // 命令式切 class
  }))
}
document.addEventListener('DOMContentLoaded', () =>
  document.querySelectorAll('[data-searchable-select]').forEach(initSearchableSelect))

依賴極少:全專案前端只用到 axios、laravel-echo、pusher-js;無任何前端框架。

盤點18 檔 ~2,077 行,依規模 / 風險分層

分層檔案行數特性
重 / 高風險 chats/index.js 534 即時(Echo/Pusher)+ 樂觀送出 + skeleton + scroll 控制,狀態最複雜
重 bills/create.js / bills/index.js 637 / 240 大型表單與列表,動態列、計算、篩選

每頁載入方式統一:Blade 內 @vite('resources/js/<feature>/<entry>.js')。這個一對一結構,是逐島遷移可行的關鍵。

3. 目標架構:Blade + Vue 島嶼

保留 Blade,把每塊互動換成掛載的 Vue 元件。

島嶼資料流(取代「JS 讀 DOM」)

Laravel Controller準備資料
Blade 渲染掛載點<div id="app" :props>
含 JSON 初始資料
@vite
entry 改 createAppmount('#app')
接管
Vue 元件響應式狀態驅動畫面
取代命令式 DOM

作法一個島的最小形狀

Blade 仍負責出頁與掛載點、把伺服器資料以 props/JSON 交給 Vue;entry 不再寫命令式 DOM,而是掛上元件:

{{-- Blade:渲染掛載點 + 注入初始資料（取代 data-* 讀取） --}}
<div id="searchable-select-app"
     data-options='@json($options)' data-name="module_id"></div>
@vite('resources/js/components/searchable-select.js')
// entry：掛載 Vue 元件,而非操作 DOM
import { createApp } from 'vue'
import SearchableSelect from './SearchableSelect.vue'

const el = document.getElementById('searchable-select-app')
if (el) {
  createApp(SearchableSelect, {
    options: JSON.parse(el.dataset.options),   // Blade → props
    name: el.dataset.name,
  }).mount(el)
}

會改變

  • 各 @vite entry 內容:命令式 DOM → createApp().mount()。
  • 互動區塊的 Blade:從「完整 HTML + class hook」改為「掛載點 + JSON 資料」。
  • 新增依賴 vue 與 @vitejs/plugin-vue,vite.config.js 加 plugin。
  • 引入 .vue 單檔元件與(選用)composable。

維持不變

  • Laravel 路由 / Controller / 驗證 / 權限 / 認證 / CSRF。
  • Blade layout、非互動的伺服器渲染 HTML。
  • Tailwind v4 設計系統(@theme token、元件類)。
  • Echo/Reverb 與 axios 設定(可沿用 bootstrap.js 或收斂成 composable)。
  • 每頁一個 @vite entry 的載入機制。

4. 遷移策略與分批

依「風險低、重用價值高」先行,聊天頁壓軸。

順序四批遷移(由易到難)

批次對象理由風險
試點 searchable-select + 一個中型表單(如 grades/form) 重用元件一改、多頁受益;同時驗證「島嶼慣例」(掛載點命名、資料傳遞、建置) 低
第二批 shops/edit · addons/form · deleteModal · 各輕量頁 中小型、邏輯單純,鞏固模式並產出可重用元件(modal、表單欄位) 低
第三批 bills/create(637)· bills/index(240) 大型表單 / 列表,動態列與計算用 Vue 響應式收益大 中
壓軸 chats/index(534,即時) 即時事件 + 樂觀送出 + scroll/skeleton 狀態最複雜,待團隊熟練後再動 高
每批皆可獨立上線、獨立回退;舊原生 JS 與新 Vue 島可在不同頁面長期並存,沒有「切換日」壓力。

5. 與現有規範的衝突 / 需決策點

遷移會踩到目前 CLAUDE.md 的前端約定,需事先定調。

注意四個需要團隊決策的點

  • 「JS 契約 class」規則會被取代 CLAUDE.md §5 現規範要求 hidden 切換、.flash-message、#delete-modal*、.delete-btn 等以字面 class 留在 element 上供 JS 操作。島內改由 Vue 狀態驅動(v-if/v-show),這套契約在島內自然消失——需更新該規則的適用範圍(島內 vs 島外)。
  • flash 與 deleteModal 是跨頁共用,要決定去留 utils/flash.js、utils/deleteModal.js 目前是全域 DOM 工具。可選擇:暫時維持全域 DOM(島外仍用)、或改寫成共用 Vue 元件 / composable。建議先維持全域,待多數頁面 Vue 化後再收斂。
  • Tailwind v4 與 SFC scoped 的並用策略 現規範用 @theme token + @apply 元件類。Vue SFC 可繼續用 Tailwind utility(token 共用),原則上少用 <style scoped>,維持單一設計系統來源,避免樣式雙軌。
  • bootstrap.js 的 Echo/axios 收斂 目前掛在 window(window.Echo、window.axios、window.refreshChatBadge)。Vue 化後宜逐步收斂成 composable(如 useEcho()),但可最後再做,初期沿用 window 不阻擋遷移。

6. 成本與風險評估

收益與代價並陳。

收益 / 優勢

  • 響應式取代命令式:不再手動 querySelector + classList,狀態一改畫面自動更新,bug 面縮小。
  • 複雜頁大幅簡化:聊天、帳單表單這類狀態多的頁,Vue 的可讀性與可維護性提升最明顯。
  • 元件重用:searchable-select、modal、表單欄位抽成元件後跨頁共用。
  • DX 與一致性:SFC 把 template/邏輯/樣式收在一起,團隊風格更一致。
  • 沿用既有基建:Vite、Tailwind、Echo 都不必換,改動侷限在「畫面層」。

成本 / 風險

  • 改寫工時:約 2,077 行、18 檔需逐一改寫並回歸測試;雖可分批,總量不小。
  • 新依賴與建置:加入 vue + @vitejs/plugin-vue,調整 vite.config.js(改動小但需驗證打包)。
  • 學習曲線:團隊需熟悉 Vue 響應式、SFC、Composition API。
  • 目前無 JS 測試:遷移正確性難自動驗證,初期高度依賴人工回歸,風險偏高。
  • 聊天頁重寫風險:即時事件順序、樂觀送出對賬、scroll 行為,改寫易引入難察覺的競態。
  • 雙重狀態邊界:島內(Vue)與島外(Blade/全域 JS)的資料同步需明確界線,避免兩邊各持一份狀態。
不在風險清單上的:本系統為內部後台、非公網暴露(對齊既有威脅模型),且採客戶端島嶼(CSR),不涉及 SEO / SSR / hydration,故省去 Nuxt/SSR 路線的整類複雜度與部署成本。

7. 建議與里程碑

怎麼開始、怎麼收尾。

建議先試點、立慣例、再規模化

  • M1 — 試點與立規先做 searchable-select + 一個中型表單;同時把 vue 依賴、vite.config.js plugin、島嶼慣例(掛載點命名、JSON 資料傳遞、元件目錄結構)定下來,並補一份島嶼開發指引。
  • M2 — 鋪開中小型頁第二批中小型頁逐一遷移,沉澱可重用元件(modal、表單欄位、flash)。
  • M3 — 大型表單遷移 bills/create、bills/index。
  • M4 — 聊天頁壓軸團隊熟練後再改 chats/index,並補上即時/樂觀送出的人工測試清單。
  • 建議補強導入前期同步建立前端測試基礎(如 Vitest + Vue Test Utils),降低「無自動驗證」風險。
範圍提醒:本評估鎖定「Blade + Vue 島嶼」。若日後目標升級為「整頁 Vue」,優先評估 Inertia.js(讓 Laravel 直接驅動 Vue 頁面、免另做 API);再上一級才是前後端分離 SPA。兩者皆為另一份評估的主題,不在本文範圍。

界定本評估刻意不做的事

不動任何程式未改 JS / Blade / vite.config.js,未安裝套件;文中程式僅為示意。
不下最終決策提供可行性、成本、風險與順序依據,是否導入由團隊定。
不展開 Inertia / SPA僅末段一句點到替代路線,完整評估另開文件。
