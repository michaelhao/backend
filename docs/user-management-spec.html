user-management Specification

使用者 CRUD、密碼政策、自我保護與刪除參照檢查的完整行為規格
威脅模型：內部後台、非公網暴露（brute-force 不在 scope）；能登入後台者即為受信任的內部人員。正式環境無對外網際網路連線——禁用 HIBP 等外部 API。帳號僅由管理員建立，無自助註冊。

使用者 CRUD

R1使用者列表

系統 SHALL 在 GET /users（需 User.index 權限）顯示所有使用者，依建立時間新到舊排列，每筆 SHALL 含名稱、電子郵件與角色名稱（eager load role，無角色時顯示「—」）。
有權限者可見使用者列表UserCrudTest::admin_can_access_user_index
GIVEN持有 User.index 權限的使用者
WHENGET /users
THEN系統回應 200 並渲染使用者列表

R3新增使用者

POST /users（需 User.create 權限）SHALL 以 StoreUserRequest 驗證：name 必填、最長 100 字元；email 必填、email 格式、最長 255 字元且不得與既有使用者重複；password 必填、須通過確認欄位（confirmed）並符合密碼強度規則；role_id 必填且須存在於 roles 表。成功 SHALL 建立使用者（密碼經 hashed cast 雜湊）、302 導向 /users 並帶 success flash「使用者已建立」。
成功建立使用者UserCrudTest::admin_can_create_user
GIVEN持有 User.create 權限的使用者
WHENPOST /users 帶合法的 name、email、password（含確認）與 role_id
THEN系統回應 302 導向 /users 並帶 success flash
AND使用者已存在於資料庫且綁定指定角色
email 重複被拒UserCrudTest::store_fails_with_duplicate_email
GIVEN已存在使用該 email 的使用者
WHENPOST /users 帶相同 email
THENsession errors 包含 email
未填密碼被拒UserCrudTest::store_fails_without_password
WHENPOST /users 不帶 password
THENsession errors 包含 password
密碼確認不一致被拒UserCrudTest::store_fails_with_password_mismatch
WHENPOST /users 的 password 與 password_confirmation 不同
THENsession errors 包含 password
role_id 不存在被拒UserCrudTest::store_fails_with_invalid_role_id
WHENPOST /users 帶不存在的 role_id
THENsession errors 包含 role_id
name 超過 100 字元被拒UserCrudTest::store_fails_with_too_long_name
WHENPOST /users 帶 101 字元的 name
THENsession errors 包含 name

R5編輯與更新使用者

GET /users/{id}/edit（需 User.update 權限）SHALL 渲染預填 name、email、role_id 的編輯表單。PUT /users/{id} SHALL 以 UpdateUserRequest 驗證，規則同新增，除了：email 唯一性檢查 SHALL 排除自身（ignore($this->route('id'))）；password 選填——留空 SHALL 維持原密碼不變（空值由 Service 層剝除），有值則須通過確認欄位與密碼強度規則。成功 SHALL 302 導向 /users 並帶 success flash「使用者已更新」。
編輯表單預填既有資料UserCrudTest::edit_form_loads_with_existing_values
GIVEN既有使用者
WHENGET /users/{id}/edit
THEN系統回應 200 且表單含該使用者的 name 與 email
密碼留空維持不變UserCrudTest::admin_can_edit_user_without_changing_password
GIVEN既有使用者
WHENPUT /users/{id} 改名且 password 留空
THEN名稱已更新
AND密碼雜湊值維持原值
填入新密碼則更新UserCrudTest::admin_can_edit_user_with_new_password
GIVEN既有使用者
WHENPUT /users/{id} 帶合規新密碼與確認
THEN新密碼可通過 Hash 驗證
email 改為他人 email 被拒UserCrudTest::update_fails_with_duplicate_email
GIVEN兩個既有使用者
WHENPUT 更新其中一人的 email 為另一人的 email
THENsession errors 包含 email

存取控制

R2權限控管

六條使用者管理路由 SHALL 受 auth middleware 與 RequiresPermission attribute 保護：index 需 User.index、create/store 需 User.create、edit/update 需 User.update、destroy 需 User.delete。未登入或無對應權限者 SHALL 被導離，且資料不得被變更。
未登入者被導向登入頁UserCrudTest::guest_is_redirected_to_login
WHEN訪客 GET /users
THEN系統回應 302 導向 /login
無 create 權限者不可見新增頁UserCrudTest::viewer_cannot_access_create_page
GIVEN僅持有 Viewer 角色權限的使用者
WHENGET /users/create
THEN系統回應 302 導離
無 update 權限者不可更新使用者UserCrudTest::viewer_cannot_update_user
GIVEN僅持有 Viewer 角色權限的使用者
WHENPUT /users/{id} 試圖改名
THEN系統回應 302 導離
AND該使用者名稱未被變更
無 delete 權限者不可刪除使用者UserCrudTest::viewer_cannot_delete_user
GIVEN僅持有 Viewer 角色權限的使用者
WHENDELETE /users/{id}
THEN系統回應 302 導離
AND該使用者仍存在於資料庫

密碼政策

全站政策集中於 app/Rules/PasswordPolicy.php 的 PasswordPolicy::default()，由各 FormRequest 明確呼叫，使用者管理與密碼重設（auth）共用。

R4密碼強度規則

使用者密碼 SHALL 符合 PasswordPolicy::default() 全站政策（定義於 app/Rules/PasswordPolicy.php，各 FormRequest 明確呼叫）：最少 12 字元、含大小寫字母、數字與符號。系統 MUST NOT 使用 Password::uncompromised()（HIBP 外部 API）——正式環境無對外網際網路連線，外部呼叫必定失敗。
新增時弱密碼被拒UserCrudTest::store_fails_with_weak_password
WHENPOST /users 帶純小寫字母的密碼
THENsession errors 包含 password
更新時弱密碼被拒UserCrudTest::update_fails_with_weak_password
GIVEN既有使用者
WHENPUT /users/{id} 帶純小寫字母的密碼
THENsession errors 包含 password

刪除與保護

刪除有三道防線：找不到（404）、刪除自己（422）、帳單業務參照（422）；通過後刪除並清除 sessions。

R7刪除使用者

DELETE /users/{id}（需 User.delete 權限）為 axios 請求（前端確認 modal 後送出），成功 SHALL 刪除該使用者、一併刪除其 sessions 表記錄（既有登入即刻失效；僅適用 SESSION_DRIVER=database），並回應 JSON 訊息「使用者已刪除」；前端隨之自列表移除該列。
成功刪除其他使用者UserCrudTest::admin_can_delete_other_user
GIVEN持有 User.delete 權限的使用者
WHENDELETE /users/{id}（非自己）
THEN系統回應 200 與 JSON {"message": "使用者已刪除"}
AND該使用者已不存在於資料庫
刪除後 sessions 一併清除UserCrudTest::deleting_user_removes_their_sessions
GIVEN目標使用者於 sessions 表存在既有 session 記錄
WHENDELETE /users/{id}
THENsessions 表不再有該使用者的記錄

R8刪除保護——帳單業務參照

使用者被 bills.shop_sales_id 參照（曾被指派為帳單業務）時，系統 MUST NOT 允許刪除，SHALL 回應 422 與 JSON 訊息「該使用者為帳單業務，無法刪除」。
bills.creator_id 與帳單狀態紀錄的操作者屬歷史稽核資料，刻意不擋刪除（否則多數使用者將永遠無法刪除），顯示層以 nullsafe 處理懸掛參照。
帳單業務不可刪除UserCrudTest::cannot_delete_user_referenced_by_bills
GIVEN某使用者被一筆帳單指派為業務（shop_sales_id）
WHENDELETE /users/{id}
THEN系統回應 422 與 JSON {"message": "該使用者為帳單業務，無法刪除"}
AND該使用者仍存在於資料庫

R9自我保護規則

操作對象為目前登入的使用者時：系統 MUST NOT 允許刪除自己的帳號（回應 422 與訊息「無法刪除自己的帳號」）；MUST NOT 允許修改自己的 role_id（302 導回前頁並帶 error flash「無法修改自己的角色」）。自己的 name、email、password SHALL 仍可正常修改。
此規則防止管理員把自己鎖出系統或意外降權（源自 spec/16 P1-1），由 UserService 強制執行（拋 UserOperationException）。多管理員互相降權不在防護範圍——威脅模型內能登入後台者即受信任的內部人員。
不可刪除自己UserCrudTest::admin_cannot_delete_self
GIVEN持有 User.delete 權限的登入使用者
WHENDELETE 自己的 id
THEN系統回應 422 與 JSON {"message": "無法刪除自己的帳號"}
AND自己仍存在於資料庫
不可修改自己的角色UserCrudTest::admin_cannot_change_own_role
GIVEN持有 User.update 權限的登入使用者
WHENPUT 自己的 id 並帶不同的 role_id
THEN系統回應 302 並帶 error flash「無法修改自己的角色」
AND自己的 role_id 維持原值
可修改自己的名稱（角色不變）UserCrudTest::admin_can_edit_own_name_without_changing_role
GIVEN持有 User.update 權限的登入使用者
WHENPUT 自己的 id 改名、role_id 維持原值
THEN系統回應 302 導向 /users 並帶 success flash
AND名稱已更新

刻意設計（不是缺漏）

以下為刻意的設計決策，避免後人誤判為待補項目或 bug。

R6找不到 id 的處理（刻意設計）

路由 SHALL 採手動 {id} 查詢（UserService::findUserById() 經 Repository），MUST NOT 使用 route model binding——找不到時以應用語意回應而非空白 404 頁（源自 spec/7 的設計決策）：edit 與 update SHALL 302 導回 /users 並帶 error flash「找不到該使用者」；destroy（axios JSON 請求）SHALL 回應 404 與 JSON 訊息「找不到該使用者」。
destroy 原回 422，2026-06-12 設計 review 修正為 404（422 語意為驗證錯誤），commit 4708b1a。
編輯不存在的使用者UserCrudTest::edit_redirects_with_error_for_missing_user
WHENGET /users/99999/edit
THEN系統回應 302 導向 /users 並帶 error flash「找不到該使用者」
更新不存在的使用者UserCrudTest::update_redirects_with_error_for_missing_user
WHENPUT /users/99999
THEN系統回應 302 導向 /users 並帶 error flash「找不到該使用者」
刪除不存在的使用者UserCrudTest::destroy_returns_404_for_missing_user
WHENDELETE /users/99999
THEN系統回應 404 與 JSON {"message": "找不到該使用者"}

R10無自助註冊與 email 驗證（刻意設計）

系統 MUST NOT 提供自助註冊端點，使用者帳號僅能由持 User.create 權限的管理員建立；MUST NOT 啟用 email 驗證流程（MustVerifyEmail 未實作）——內部後台，使用者即受信任的內部人員，帳號由管理員開立即視為有效。
無註冊路由無直接測試 — route:list 驗證無 /register 路由
WHEN訪客 GET /register
THEN系統回應 404（路由不存在）

—刻意不做的事（彙整）

自助註冊帳號僅由持 User.create 權限的管理員建立，無 /register 路由（R10）
Email 驗證流程MustVerifyEmail 未啟用，內部人員帳號由管理員開立即視為有效（R10）
HIBP uncompromised()正式環境無對外網際網路連線，外部 API 呼叫必定失敗（R4）
Route model binding保留 {id} + redirect-with-flash UX，找不到使用者回列表頁而非 404 頁（R6）
歷史稽核參照擋刪除bills.creator_id 與狀態紀錄操作者不擋，否則多數使用者永遠無法刪除；顯示層 nullsafe 處理（R8）
多管理員互相降權防護自我保護僅防誤操作；能登入後台者即受信任的內部人員（R9）
