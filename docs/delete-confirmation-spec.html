delete-confirmation Specification

roles / users / addons 列表共用的前端刪除互動契約（axios DELETE + 確認 modal + flash + DOM 移除 + CSRF）
威脅模型：內部後台、非公網暴露；正式環境無對外網際網路連線（單檔文件零外部資源）。
來源：openspec/specs/delete-confirmation/spec.md 合併自：spec/10-fix-form-post-axios.md 實作：b824d18、65068af、98b84e5 change：2026-06-14-retrofit-delete-confirmation-spec
本頁為人工同步的閱讀版；若與 spec.md 不一致，以 spec.md 為準。逐資源的業務規則見 role-management / user-management / addon-management spec。前端互動 Scenario 無自動化測試（以橘色標註），DELETE JSON 契約則對應 feature 測試。

互動流程圖

三頁共用同一條前端流程；後端 destroy 回傳統一的 JSON 契約。

刪除互動（列表頁）

點擊 .delete-btn帶 data-url / data-name
開啟 #delete-modal填入 data-name
取消 / Esc / 點背景可關閉
確認
axios DELETE(data-url)禁用鈕、顯示「刪除中...」
自動帶 XSRF-TOKEN cookie
回應
2xx：移除對應 <tr> → flash(success, server message)
非 2xx：保留該列 → flash(error, res.data.message)

destroy 端點 JSON 契約（後端）

DELETE /{resource}/{id}
解析資源
可刪除 → 200 {message}
找不到 → 404 {message}
業務拒絕 → 422 {message}

前端互動

R1刪除按鈕觸發確認 modal

列表頁的刪除入口 SHALL 為 type="button" 的 .delete-btn，帶 data-url（DELETE 目標 URL）與 data-name（顯示名稱），MUST NOT 為 inline <form>。點擊 .delete-btn SHALL 開啟該頁共用的 #delete-modal，並將 data-name 填入 #delete-modal-name。Modal SHALL 可由「取消」鈕、Escape 鍵、或點擊 overlay 背景關閉，關閉時清除待刪目標。
點擊刪除開啟確認 modal無自動化測試 — 前端互動（utils/deleteModal.js）
GIVEN列表含一筆資料、其刪除鈕帶 data-url 與 data-name
WHEN使用者點擊該 .delete-btn
THEN#delete-modal 顯示，且 #delete-modal-name 為該筆 data-name
取消 / Esc / 點背景關閉 modal無自動化測試 — 前端互動（utils/deleteModal.js）
GIVEN#delete-modal 開啟中
WHEN使用者點「取消」、按 Escape、或點 overlay 背景
THENmodal 關閉且不送出任何請求

R2確認後送 axios DELETE

確認鈕按下時，前端 SHALL 以 window.axios.delete(data-url) 送出請求，過程中 SHALL 禁用確認鈕並顯示「刪除中...」。回應 2xx 時 SHALL 自 DOM 移除該列對應的 <tr>，並以 server 回傳的 message 顯示成功 flash。回應非 2xx 時 SHALL 保留該列，並以 res.data.message（無則通用訊息）顯示錯誤 flash。無論成功或失敗，結束時 SHALL 關閉 modal、還原確認鈕狀態。
刪除成功移除列無自動化測試 — 前端 DOM 行為
GIVEN確認 modal 指向某列的 data-url
WHENaxios DELETE 回應 200
THEN該列 <tr> 自 DOM 移除
AND顯示成功 flash，內容為 server 回傳的 message
刪除失敗保留列並顯示訊息無自動化測試 — 前端 DOM 行為
GIVEN確認 modal 指向某列的 data-url
WHENaxios DELETE 回應非 2xx（含 422 / 404）
THEN該列保留於畫面
AND顯示錯誤 flash，內容為 res.data.message

R3flash 訊息機制

前端動態 flash SHALL 由 resources/js/utils/flash.js 提供：showFlash(type, message) SHALL 將訊息插入 .flash-area 並於 5 秒後淡出移除；autoDismissFlashes() SHALL 對既有 server 端 .flash-message（session('success') / session('error') 渲染者）套用相同的 5 秒淡出。頁面 SHALL 提供 .flash-area 容器供插入。
動態 flash 自動淡出無自動化測試 — 前端互動（utils/flash.js）
WHENshowFlash('success', '角色已刪除') 被呼叫
THEN.flash-area 內出現該訊息
AND約 5 秒後自動淡出移除

安全與契約

R4CSRF 採 axios 預設 XSRF cookie

刪除請求的 CSRF 保護 SHALL 依賴 axios 內建的 XSRF-TOKEN cookie → X-XSRF-TOKEN header 機制（Laravel 每個 response 自動下發 XSRF-TOKEN cookie，VerifyCsrfToken 接受該 header）。resources/js/bootstrap.js SHALL 設定 X-Requested-With: XMLHttpRequest。系統 MUST NOT 依賴頁面手動以 meta[name=csrf-token] 設定 X-CSRF-TOKEN 作為刪除請求的 CSRF 來源。
帶 CSRF 的 DELETE 通過驗證無直接測試 — feature test 不經 VerifyCsrfToken；目視 bootstrap.js
GIVEN已登入的 session（持有 XSRF-TOKEN cookie）
WHEN前端以 axios 送出 DELETE
THEN請求通過 CSRF 驗證並抵達 controller（非 419）

R5destroy 端點共用 JSON 契約

採本互動的 destroy 端點（DELETE /roles/{id}、DELETE /users/{id}、DELETE /addons/{id}）SHALL 一律回傳 JSON { "message": ... }，MUST NOT 回 redirect。狀態碼語義 SHALL 一致：成功回 200；找不到資源回 404；業務規則拒絕回 422。逐資源的成功訊息、業務拒絕條件與連帶副作用（pivot / sessions 清理、軟刪除等）SHALL 依各自 capability：role-management、user-management、addon-management。
本需求是三頁刪除的共用 JSON 契約；具體業務規則（哪些角色不可刪、刪 user 連帶清 sessions、addon 軟刪除等）不在此重述，請見對應 module spec。
成功回 200 JSONPermissionTest::test_role_crud_delete · UserCrudTest::test_admin_can_delete_other_user · AddonCrudTest::test_admin_can_soft_delete_addon
GIVEN持有對應 delete 權限的使用者
WHENDELETE 一筆可刪除的資源
THEN系統回應 200 與 JSON {message}（資源已自畫面移除）
找不到資源回 404PermissionTest::test_destroy_nonexistent_role_returns_404 · UserCrudTest::test_destroy_returns_404_for_missing_user · AddonCrudTest::test_destroy_returns_404_for_missing_addon
WHENDELETE 一個不存在的 id（roles / users / addons 任一）
THEN系統回應 404 與 JSON {message}
業務規則拒絕回 422PermissionTest::test_cannot_delete_role_with_users · UserCrudTest::test_admin_cannot_delete_self · UserCrudTest::test_cannot_delete_user_referenced_by_bills
GIVEN一筆因業務規則不可刪除的資源（如仍有使用者的角色、帳單業務、刪除自己）
WHENDELETE 該資源
THEN系統回應 422 與 JSON {message}
AND該資源仍存在

刻意設計（不是缺漏）

以下為刻意的設計決策，避免後人誤判為待補項目。

R6不採用 inline form POST + 原生 confirm（刻意設計）

刪除互動 MUST NOT 使用「表格內 inline <form method=POST> + @method('DELETE') + onsubmit=confirm()」的整頁 reload 舊法。此舊法已於 commit b824d18 自三頁移除，改為本 capability 描述的 axios + 自訂 modal 流程。
列表不含 inline 刪除表單無自動化測試 — 目視 blade template
WHEN渲染 roles / users / addons 列表
THEN列內刪除入口為 .delete-btn 按鈕，畫面不含 per-row 的刪除 <form>

R7不抽共用 modal 元件（刻意設計）

各列表頁 SHALL 自行於 blade 維護其 #delete-modal 標記，系統 MUST NOT 將 modal HTML 抽為共用 blade component。互動邏輯則 SHALL 共用 resources/js/utils/deleteModal.js 的 initDeleteModal()，避免三頁 JavaScript 重複。
modal HTML 各頁自維護、JS 邏輯共用無自動化測試 — 目視 blade + index.js
WHEN檢視三頁的刪除實作
THEN各頁 blade 各有自己的 #delete-modal 標記
AND三頁 index.js 皆 import 同一個 utils/deleteModal.js 的 initDeleteModal

—刻意不做的事（彙整）

inline form POST + confirm()已由 axios + 自訂 modal 取代（R6），不再整頁 reload
共用 modal blade 元件各頁自維護 modal HTML；只共用 JS 邏輯 deleteModal.js（R7）
手動 meta X-CSRF-TOKEN改用 axios 預設 XSRF-TOKEN cookie 機制（R4）
